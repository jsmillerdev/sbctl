# internal/selfupdate

`supavise self-update` as a library: `Update(ctx, Options)` replaces a binary with a GitHub release after verifying it, `Latest` reads the release, `Newer` compares versions.

A release holds `supavise-linux-amd64`, `supavise-linux-arm64`, `SHA256SUMS` (sha256sum format), `SHA256SUMS.sig`, the raw 64-byte ed25519 signature of the `SHA256SUMS` file, and `supavise-release.json`, the release manifest, which `SHA256SUMS` lists. `deploy/release-assets.sh` produces them with `openssl pkeyutl -sign -rawin`; the OpenSSL signature in `testdata/` proves that Go's `crypto/ed25519` verifies what OpenSSL signs.

Order of events in `Update`: resolve the release, stop if it is not newer (or `Force`), download `SHA256SUMS` and the signature, verify the signature against the keys (`release_key.pem`, and `release_key_next.pem` when it holds a key, both embedded in the binary; or `Options.Keys` or `Options.Key`), download the manifest and check it against the checksum the signed list holds for it and against the release tag, refuse a release whose `min_upgrade_from` is newer than the running version (`Force` skips that), read the checksum of the binary asset from the signed list, stream the binary into a temp file next to the target while hashing, compare, `chmod 0755`, run it with `--version` and require its output to name the release tag, hard-link the old file as `<name>.prev`, rename the new file over the target. Every failure before the rename leaves the installed binary and the directory as they were. No key (the placeholder file), an unsigned release, a list that omits the platform, a binary that does not match, a binary that does not start and a binary that reports another version than the tag it was published under (an older signed release attached to a newer tag) are all refusals with their own message (tests in `selfupdate_test.go`).

`release_key.pem` holds the public key. It is a placeholder until the maintainers commit one (`deploy/README.md`, Release signing); with the placeholder `Update` returns `ErrNoKey` before it touches the network. `release_key_next.pem` is empty (also a placeholder) except during a key rotation: while it holds a key, a signature by either key is accepted, so that the release that introduces the next key and the release signed with it both install on a node without a reinstall (`deploy/README.md`, "Rotating the release signing key"; `EmbeddedKeys`, `VerifySumsAny`, `TestKeyRotationNeedsNoReinstall`). `DefaultRepo` and the two key files are the only build-time inputs.

## The release manifest (for `supavise upgrade`)

`manifest.go` defines the signed manifest (`deploy/README.md` has the field table): `schema`, `version`, `min_upgrade_from`, `artifacts` (the slim-services tag of each Supabase service) and `studio`. The functions the upgrade engine calls:

- `Fetch(ctx, Options) (*Verified, error)` resolves the release (`Options.Tag`, or the latest stable one), verifies the signature of `SHA256SUMS` against the embedded keys, checks the manifest against the signed list and against the release tag, and returns the release, the signed list, the manifest and which key signed. It downloads only those three small files. `Verify(ctx, Options, *Release)` does the same for a release already resolved.
- `(*Manifest).CheckUpgradeFrom(current) error` is nil when a node on `current` may upgrade straight to the release, and otherwise the refusal that names the version to go through first. A `current` that is not a release version passes.
- `(*Verified).Stage(ctx, Options) (*Staged, error)` downloads the binary of the verified release for `Options.Platform`, checks it against the signed list and runs it with `--version` (the tag it reports must be the release's), into `Options.StageDir` or the directory of `ExecPath`; nothing installed changes. `(*Staged).Install()` is then one rename (the old binary stays as `<name>.prev`), `Discard()` removes the file. `Update` is `Fetch`, `Stage`, `Install`; `supavise upgrade` stages the binary first, asks it for its pins (`supavise release-info`) and installs it only after the node has been backed up. `(*Verified).Studio(platform)` names the dashboard build the signed list carries (`supavise-studio-*-<platform>.tar.zst`), `Compare(a, b)` orders two release tags.
- `ParseManifest`, `(*Manifest).Marshal` (deterministic bytes) and `Validate`.
- `ChecksumFor(sums, name)` on `Verified.Sums` gives the signed checksum of any other asset, so the engine can download the binary itself and still trust only what the signature covers.

A release without a manifest, or with one that does not match its listed checksum, is refused with its own message (`manifest_test.go`, `selfupdate_test.go`). The writer is `deploy/releasetool manifest`, called by `deploy/release-assets.sh`.

Downgrade protection: the signature covers the checksums, not the tag, so the tag-versus-`--version` check is what stops a downgrade through re-attached assets. `--version` or `--force` can still install an older release that was honestly published under its own tag. The signed manifest now names the version, so the same check holds without running the binary. Not done: delta updates.
