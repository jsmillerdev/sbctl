# internal/nodeupgrade

`supavise upgrade` and `supavise rollback`: they move a whole node, the binary, the shared services and the projects, onto a newer release of Supavise, and back. A release is a tested bundle of a binary and the Supabase service versions pinned in its `versions.yaml`. `deploy/README.md`, "Upgrading the node", is the operator's view; this is the code's.

The package holds the parts that decide things and talks to the machine through one interface, `Host`, so the order of the steps and every failure path run in unit tests without a server. `cmd/supavise/upgrade_host.go` implements `Host` for a Linux node.

Files: `info.go` (`Info`, the release a binary is, from `supavise release-info`: version, pins, embedded registry migrations; `DiffPins`, `CheckManifestPins`), `node.go` (`Node`, what `Host.Inspect` learns before anything changes), `plan.go` (`BuildPlan`, `CheckGates`, `DiskNeeded`), `run.go` (`Run`, `Failure` and the exit statuses, the marker phases, the automatic rollback), `rollback.go` and `rollback_run.go` (`CheckRollback`, `rollBackTo`, `Rollback`), `releases.go` (`Releases`: the kept binaries and their records, `GC` for `keep_releases`).

## The order

1. **Check.** `Host.Resolve` finds the newest release (or `--version`) through `selfupdate.Fetch`: the signature of `SHA256SUMS` against the embedded keys, the signed manifest against its checksum and the tag. `min_upgrade_from` refuses a jump over a release it needs (exit 2), and so does a release older than the installed one.
2. **Plan.** `Host.Stage` downloads the new binary next to the installed one, verifies it against the signed list and runs `release-info` on it; its pins must equal the manifest's. `BuildPlan` diffs them against what the node runs: the shared services and the system project (read from the launcher scripts the daemon rendered, `fleet.RenderedTag`) and the projects' recorded versions. A project's PostgreSQL moves only with `--include-postgres`; a shared service the node never rendered is left out. `--check` and `--plan` stop here, and `--check` reads only the installed version (`VersionInspector`), so it needs neither the registry nor an idle node.
3. **Gates**, all exit 2 with nothing changed: the node is down; the disk cannot hold the new artifacts (and a compressed copy of every project when backups are local; unreadable free space is a warning, and a refusal with `--unattended`); another upgrade runs; the new release moves PostgreSQL to another major version. With `--unattended` also: the node is not healthy, a running project has no backup newer than 24 hours, or the status report's `key escrow` component does not say ok. Interactively the escrow state is a warning, and the plan asks for a yes unless `--yes` is given.
4. **Prepare**, still changing nothing that runs: the staged binary fetches every artifact that moves (`artifacts fetch`, as the supavise user; it opens no registry), then a base backup of the system project and of every running project, three at a time, as the supavise user on the installed binary. A failure of either is exit 2.
5. **Apply.** The running release and the new one are kept (`Releases`), the binary is swapped in with one rename, `system install-units` renders the units with it, and `supavise.service` restarts and is waited for. The new daemon rolls the shared services itself, one at a time and each waited for (`fleet.Manager.Start` restarts a service whose files changed); while the marker says an upgrade runs, the first failure ends the roll, and `Host.WaitShared` checks that each service is set to run its new release, has restarted since the swap and answers. Then `projects upgrade --all --restart-changed --to gotrue=... --to postgrest=...` on the new binary moves the projects, `[upgrade] canary_projects` first, then `batch_size` at a time, stopping at the first failure; each project reuses this run's backup (`--reuse-backup-since`). A change of binary that moves no release still runs the rollout: while the marker says the upgrade moves forward, the new daemon renders every project's PostgreSQL, GoTrue and PostgREST files and leaves running units on the old ones (`lifecycle.DeferRestarts`; a restarted PostgreSQL takes that project's GoTrue and PostgREST down with it, so the rollout restarts all three), and `--restart-changed` adds those projects to the same canary and batches. The plan cannot name them and says so. The system cluster restarts at the daemon's start when its files changed, outside the rollout, and the plan names that restart.
6. **Verify.** `supavise status` must be no worse than before, polled for up to five minutes (services say COMING_UP for a while after a restart). Then `artifacts gc` and the kept-release `GC` run.

A failure from the swap on rolls back (`rollBackTo`): the registry rule first (below), then the projects this run moved go back to the releases they ran (`projects upgrade <ref> --yes --no-gc --allow-older --to ...`, one command per project, on the new binary, which still runs; `projectReverter` in `cmd/supavise/upgrade_revert.go` judges a project by where it ends: a failed command that left it healthy on its old releases counts as reverted, one that left it elsewhere runs once more, and a failure that stays is reported), then the kept binary is installed again, the units rendered, the daemon restarted, the shared services waited for on their old releases, the verdict checked. A service counts as back when its unit is set to run the old release and answers; it has to restart after the swap only if the swap moved it (`mustHaveRestarted`). Exit 3 when the node is back and as healthy as before; exit 4 when it is not, or when the rule refuses (the projects still go back then).

An upgrade that does not change the binary (the services and projects are brought onto the release the installed binary already is, for example after `supavise update`) has no kept binary to go back to, so a failure runs `revertProjectsOnly`: it puts back the projects this run moved and checks the node. Exit 3 when they went back and the node is as healthy as before; exit 4 when a shared service did not come up (no rollback of this run can change what the binary pins; `supavise rollback` goes to the previous kept release) or a project did not go back.

## Alerts

`Options.Notify` receives an `Event` (`events.go`) when the node is about to change and when the run ends: the package sends no message itself. `cmd/supavise/upgrade_alerts.go` turns each event into an `internal/alerts` event with `alerts.New(cfg, ...)`, because `supavise upgrade` and `supavise rollback` run in their own process, as root, outside the daemon; they share the daemon's destinations, hourly cap and state file (`internal/alerts`, "Root and the supavise user").

| Event | When | Alert |
|---|---|---|
| `started` | after the artifacts are fetched and the backups are taken, before the binary is swapped: nothing that runs has changed until now, so a run that is refused earlier says nothing | `upgrade_started`, info |
| `succeeded` | the node runs the new release and its status is no worse than before | `upgrade_succeeded`, info |
| `rolled_back` | the change failed and the node is back on the previous release (exit status 3); names the release, the cause and the project the rollout halted at | `upgrade_failed`, warning |
| `needs_operator` | the change failed and the node is not back (exit status 4); the cause says what state it is in | `upgrade_failed`, critical |
| `refused` | only after `started`: the run stopped before it changed anything (the new binary could not be installed) | `upgrade_failed`, warning |

`supavise rollback` sends `started`, `succeeded` and `needs_operator` with `Rollback` set. Every alert says who started the run (`Unattended`: the maintenance window) and the from and to versions. A maintenance window or the upgrade marker does not hold these back: they quiet the daemon's checker, not the announcements of the upgrade (an upgrade that fails inside an announced window is told), and the announcements are not de-duplicated, so a second failed upgrade is news. A destination that is down is logged and never fails the upgrade; the delivery gets 90 seconds and survives the SIGTERM that stopped the upgrade. The halted project comes from the rollout worker's error (`haltTee` reads its stderr, `HaltReporter`): the worker prints the ref in `rollout halted: <ref> failed`, and it is the only place it is told.

**What this does not cover.** The driver of an upgrade is the installed binary, not the one being installed, so the first upgrade from a release that has no alerts sends none, and an upgrade the daemon of the old release cannot report stays in the journal. A run killed with SIGKILL, or a node that loses power mid-upgrade, sends nothing: the marker (`upgrade.json`) and `supavise status` show it, and `supavise-upgrade.service` pauses automatic upgrades (`unattended_upgrade_interrupted` in the journal).

## Exit statuses

| Status | Meaning |
|---|---|
| 0 | upgraded, or nothing to do |
| 2 | refused by a check, or the prepare step failed: nothing that runs was changed |
| 3 | failed and rolled back |
| 4 | failed and the node needs the operator: the rollback was refused or did not finish; the message says what state the node is in |

`main` turns a `*Failure` into the process's status. `internal/update` reads these statuses.

## The registry rule

Registry migrations only go forward. `CheckRollback` compares sets: the registry may hold only migrations the release to go back to knows. It does not compare the newest name, because the lanes of the project number their migrations in separate ranges. A kept record carries the migrations its binary embeds (`release-info`), or, for a binary built before it could say, the ones the registry held when the upgrade kept it. A rollback the rule refuses before it starts is exit 2 and says to put the registry back first; the same command then goes through. The way back is by hand: restore the system cluster from the pre-upgrade base backup with the control plane stopped (`internal/backup/README.md`, "Disaster recovery of the system cluster"); `supavise backups restore` refuses the system project, and the upgrade does not script the restore. An automatic rollback the rule stops is exit 4 and leaves the node on the new binary; the projects the run moved still go back, because the binary that runs reads its own schema. The plan says this for a release that adds migrations (`NewMigrations`) and promises an automatic rollback only for a release that adds none: a new daemon that fails before it applies them leaves the registry alone.

## Files

- `<state_dir>/system/upgrade.json`, written at each phase change and every ten minutes: `phase`, `from`, `to`, `started_at`, `pid`, `detail`. It is the `notice.Upgrade` marker that `supavise status` and the alert checker read. The upgrade runs as root and the directory belongs to the supavise user, so the file's owner is set on the open temporary file before the rename (`notice.WriteUpgradeAs`), never by path afterwards, which would follow a symlink put there in between. Phases: `preparing`, `switching`, `services`, `projects`, `verifying`, `rolling_back`; at the end `done`, `rolled_back`, `failed` or `refused` (the file stays). A second `supavise upgrade` refuses while the marker is fresh and its `pid` is alive.
- `/usr/local/lib/supavise/releases/<version>/{supavise,release.json}`, owned by root (`<prefix>/lib/supavise/releases` for a binary in `<prefix>/bin`), because the supavise user can write the state directory and a rollback runs the kept binary as root. `release.json` holds the pins, the migrations, the SHA-256 of the binary (checked before a rollback installs it), `installed_at` and `upgrade_started_at` / `upgrade_ended_at`, the window of the upgrade that installed the release. `supavise rollback` puts back the projects whose upgrades began inside that window (`Host.MovesBetween`, which folds a project's upgrades in the window into one move from the registry's upgrade history), so a project an Owner upgraded later keeps its releases and a second rollback still finds the moves of the release the first one went back to. A record with a start and no end (an upgrade that never finished, or whose end could not be written after four tries) puts back no project, because an Owner's later upgrade could not be told from the upgrade's moves; the rollback says so. A record without a start uses `installed_at`. `[upgrade] keep_releases` (default 3) counts the current release. A release the node was rolled back from is marked `withdrawn`, so a second rollback keeps stepping backwards.
- `/run/supavise-maintenance.lock`: the host lock (`update.LockHost`), held from before the first change until the end, so the OS reboot in the maintenance window never lands in the middle.

## Who runs what

`supavise upgrade` runs as root, because the binary and the unit files are root's. Everything that touches the node's data runs as the supavise user: root starts the worker with that user's uid, gid and groups on the child process (`SysProcAttr.Credential`), not through `runuser`, whose PAM watcher would SIGKILL the worker two seconds after a SIGTERM and cut a project upgrade off between its steps. A cancelled upgrade signals the worker directly; it rolls its project back and settles it, with two minutes to do that. The workers are the backups, the artifact fetch, `status` and the project upgrades. Root itself reads the registry (over the system cluster's private socket, without migrating it: `registry.OpenExisting`) and the launcher scripts, replaces the binary, renders the units and restarts the daemon. Before the swap the workers run on the installed binary, so a newer driver does not migrate the registry before the backups are taken.

**Which binary root runs.** The supavise user owns `/etc/supavise/config.toml`, so nothing root executes, copies or replaces comes from it. `bin_path` must be `config.DefaultBinPath` (`/usr/local/bin/supavise`); any other value is exit 2 (`installedBinary`). That file must pass `requireRootOwned` before the first command runs, even for `--check`: a regular file owned by root and not writable by group or others, in directories root owns that are not writable by group or others, up to `/` (a symlink on the way must be root's too, and its target is checked the same way); otherwise exit 2. The kept-release directory is derived from that checked path alone.

## Tests

`go test ./internal/nodeupgrade/` runs unit tests over a fake `Host`: the plan, the gates, the sequence of a good upgrade, every refusal, each failure and rollback path, the registry rule, and the release store. `tests/linux/upgrade-e2e.sh` (the `upgrade-e2e` job of `linux.yml`) runs the upgrade and rollback on a real node.

## Limits

- No zero-downtime daemon restart: the proxy lives in the daemon, so HTTPS fails for a few seconds and WAL archiving pauses.
- A project's PostgreSQL is not upgraded across a major version.
- A killed `supavise upgrade` is not resumed; run it again and it converges. The daemon settles a project left `UPGRADING`. A restart the daemon held back is recorded in a mark (`<svc>.held` next to the unit's env file) that `Host.Inspect` reads into `Project.HeldRestart`, and the plan lists those projects (`Plan.Pending`), so a rollout cut short finishes with the next `supavise upgrade`. A later start of the daemon never restarts a PostgreSQL cluster for a mark; it does restart GoTrue and PostgREST.
- Going back to the previous release restarts, one after another and outside the canary and batches, every project whose PostgreSQL, GoTrue or PostgREST files the rollout had already restarted onto the new release's files, and each restart drops the project's database connections. A unit the rollout never reached keeps running. A previous release built before the marks existed restarts every project whose files differ. The plan and the output of `supavise rollback` say so.
- The upgrade does not restore the registry. The system cluster's restore is a documented manual procedure, not tested end to end.
- A project rollback puts GoTrue back on the release it ran; GoTrue's migrations went forward and stay, and the older GoTrue runs on the newer schema.
- Events are log lines (`upgrade_started`, `upgrade_succeeded`, `upgrade_failed`, `upgrade_rolled_back`, `upgrade_refused`, `upgrade_needs_operator`, `rollback_started`, `rollback_succeeded`, `rollback_failed`) in the journal; the alerts (Alerts, above) are separate.
