# 07 - Thin install paths: installers, AWS one-click, wildcard TLS, supervision, S3

Researched 2026-10-06. Facts below are from live sources (URLs in each section). Items marked **[ANALYSIS]** are my recommendations; items marked **[UNVERIFIED]** I could not confirm from a primary source. The name `sbctl` is a placeholder for our single control-plane binary.

## TL;DR

1. **The recurring installer recipe** is: one static binary or one `curl | bash`, a dedicated system user, a systemd unit, a config file under `/etc`, a first-run "claim" step, built-in or sidecar ACME, and self-update by re-running the installer or an `update` subcommand. The weak spot in Coolify and Dokploy is first-run admin: the first visitor to `http://ip:8000` (Coolify) or `:3000` (Dokploy) becomes admin. Pangolin's setup token (read from logs) is the better pattern.
2. **Envoy cannot do ACME.** Envoy's CertificateProvider issue (#19308) was closed "not planned". The cheapest fix that keeps Envoy: embed **CertMagic** (Apache-2.0; ACME, every libdns DNS provider, on-demand TLS) in `sbctl`, write cert files, and let Envoy hot-reload them via **file-based SDS with `watched_directory`**. Alternative: replace Envoy with Caddy at the edge.
3. **AWS primary = CloudFormation quick-create link** (one EC2 on Ubuntu 24.04 + instance profile + S3 bucket + SG + EIP; UserData runs `install.sh`). **Secondary = Terraform module** around the same `install.sh`. A Marketplace AMI is a later discovery channel (7-10 business days to publish). **Supabase does not publish public AMIs**: the Packer configs build into one Supabase-owned region with no `ami_groups`/`ami_users`, so there is nothing to reference.
4. **Default TLS/DNS**: user-supplied domain, wildcard A record `*.api.<domain>`, one wildcard cert via DNS-01 (Route 53 via the instance role on AWS, Cloudflare/Hetzner/DO token elsewhere). If the user cannot give DNS credentials, fall back to per-project on-demand HTTP-01 certs (Let's Encrypt allows 50 new certs per registered domain per 7 days; ARI renewals are exempt). Zero-config trial = `<ref>.api.<dashed-ip>.sslip.io`. Path-based `/<ref>/...` also works with Realtime and Storage **only if the edge rewrites `Host` and `X-Forwarded-Host`**.
5. **Supervision**: hybrid. Per-project systemd template units (`sb-postgres@<ref>.service`, as Debian does with `postgresql@17-main`) generated by `sbctl`, with a per-project slice for `MemoryMax`/`CPUQuota`; a built-in child supervisor only as a fallback for non-systemd hosts. **Correction to the brief:** Supabase's own `services.slice` carries no limits; it only groups units. The one limit in their ansible is `MemoryMax=50%` on GoTrue. My local measurement: PG 17.11 cold start 0.20 s, idle footprint 15-20 MB (macOS, empty cluster).
6. **Storage**: AWS = real S3. Own machine = Storage API `STORAGE_BACKEND=file` (the setting in Supabase's official docker-compose) and nothing extra. **Do not bundle MinIO**: the repo was archived 2026-04-25, the README says "no longer maintained", and it ships source-only. Optional bundle when an S3 endpoint is needed: **Garage** (AGPL-3.0, single binary, v2.4.1). RustFS 1.0.0 went GA on 2026-09-16, which is too young to default to.

### The recurring recipe

1. **One entry point**: `curl | bash` (Coolify, Dokploy, Pangolin, flyctl) or a single binary (PocketBase, Forgejo, Headscale). None needs a language runtime on the host except Kamal (Ruby).
2. **A root-owned, idempotent installer** that preserves existing secrets (Coolify merges its env file and keeps existing values).
3. **systemd** when there is no Docker (PocketBase, Forgejo, Headscale, Caddy); Docker/Swarm otherwise. Coolify and Dokploy pay for Docker (a package, daemon config, networking, 30 GB disk), which we are avoiding.
4. **Auto-TLS is table stakes** (Traefik, Caddy, kamal-proxy, autocert). Wildcard certs are the exception: only Caddy/Traefik/lego with DNS-01 do them; Headscale, PocketBase and kamal-proxy do not.
5. **IP-only trial path**: Coolify offers `sslip.io`, Dokploy `traefik.me`; both are HTTP-only in practice. This is the known weak spot for anything that needs HTTPS (browsers, secure cookies).
6. **First-run bootstrap**: a web "first visitor wins" page (Coolify, Dokploy, Forgejo; fragile on a public IP), a CLI superuser command (PocketBase, Headscale), or a setup token (Pangolin). Token or CLI is the safer pattern.
7. **Config**: one file under `/etc/<name>/` (Headscale `config.yaml`, Forgejo `app.ini`, Caddyfile) or a generated env file (Coolify). Secrets generated at install.
8. **Updates**: re-run the installer (Dokploy, Coolify), a built-in `update` (PocketBase), or the package manager (Headscale, Caddy).

### Envoy and ACME

- Envoy has no ACME. Issue #96 "ACME support" is long-open and #19308 "Implement CertificateProvider mechanism" is **closed as not planned** (stale). The practice is an external manager (cert-manager, a certbot sidecar, or the community `envoy-acme-xds`).
- Envoy **can** hot-reload certs from disk: SDS via `path_config_source` watches file moves, and `watched_directory` supports atomic symlink swaps.
- Options, in order of my preference **[ANALYSIS]**:
  - **A. Embed CertMagic in `sbctl`** (Apache-2.0; HTTP-01, TLS-ALPN-01, DNS-01 for every libdns provider; on-demand TLS; RFC 9773 ARI). `sbctl` writes `fullchain.pem`/`key.pem` plus an SDS file; Envoy picks up renewals with no restart. One binary, one owner for certs.
  - **B. Caddy replaces Envoy** as the edge. Fewest moving parts and best ACME, but loses Envoy's xDS/Lua ecosystem and the Supabase gateway rules; needs a per-project route writer (Caddy admin API).
  - **C. lego** as a subprocess (300+ DNS providers including Route 53, Cloudflare, Hetzner, DigitalOcean). Works, but adds a second binary.

### 2.1 Comparison

### 2.2 Recommendation **[ANALYSIS]**

- **Primary: CloudFormation quick-create link.** Zero local tooling, works in a browser, one template that doubles as documentation. Resources: EC2 (Ubuntu 24.04 via SSM public parameter; Graviton or x86 selectable), instance profile (scoped S3 bucket access, `route53:ChangeResourceRecordSets` limited to the given zone, SSM core), S3 bucket (objects + backups), security group (22 off by default; 80/443; 5432/6543 optional), Elastic IP, optional Route 53 records, and a CloudFormation-generated Secrets Manager secret for the first-run claim token.
- **Secondary: Terraform module** that applies the same cloud-init and the same `install.sh`. Later: a Marketplace AMI as a discovery channel only.
- **ACM is not a fit on EC2**: ACM public certs normally attach to ELB/CloudFront/API Gateway. Exportable public certs (June 2025) were priced per name ($15 per FQDN, $149 per wildcard at launch; a later cut to $7/$79 for 198-day certs came from a secondary result, not confirmed on the pricing page). Let's Encrypt DNS-01 with the instance role costs nothing.
- **Base OS**: Ubuntu 24.04, not Amazon Linux 2023 (glibc 2.34). slim-services artifacts record a glibc floor of 2.35 (bundled loaders for most services, but the manifest `os_floor` is the safe reference). SSM parameter: `/aws/service/canonical/ubuntu/server/24.04/stable/current/arm64/hvm/ebs-gp3/ami-id`.

**No evidence of any.**
- `amazon-arm64-nix.pkr.hcl` (supabase/postgres, `develop`): `ami_regions` is a single-region variable (default `ap-southeast-1`); `source_ami_filter` is Canonical Ubuntu 24.04 arm64 (owner 099720109477); **no** `ami_groups`, `ami_users` or `snapshot_users`. - The platform AMI also carries closed binaries (adminapi, admin-mgr, supabase-admin-agent) fetched from `supabase-public-artifacts-bucket.s3.amazonaws.com`, and it has none of Storage, Realtime, Edge Runtime or Supavisor. ## 3. Wildcard DNS and TLS for `<ref>.api.<domain>`

### 3.1 Facts

- **Wildcard certs need DNS-01.** Caddy docs: "Wildcard certificates require the DNS challenge"; only the leftmost label may be `*`. Route 53 works with EC2 instance roles and no stored secret (caddy-dns/route53 supports instance roles; a restricted IAM policy limited to `_acme-challenge` TXT records exists). lego covers Route 53, Cloudflare, Hetzner and DigitalOcean (300+ providers); CertMagic covers every libdns provider.
- **Let's Encrypt limits**: 50 certificates per registered domain per 7 days; 300 new orders per account per 3 hours; 5 authorization failures per identifier per hour. ARI-coordinated renewals are exempt from all rate limits; non-ARI renewals with an identical identifier set are exempt from the first two. Per-project (non-wildcard) certs therefore cap new projects at about 50 a week per registered domain; one wildcard avoids that.
- **On-demand TLS** (Caddy/CertMagic) obtains a cert per hostname at first handshake via HTTP-01 or TLS-ALPN-01. It must be restricted by an authorization hook (ours: "is this ref a known project?").
- **sslip.io / nip.io** (merged): resolve any hostname containing an IP, such as `<ref>.1-2-3-4.sslip.io`, to that IP. Let's Encrypt certs are possible via **HTTP-01 only; no wildcards**. The service is not on the Public Suffix List, so its budget is shared by all users; it had a rate-limit exhaustion incident (cunnie/sslip.io issue #108) and Coolify's docs say HTTPS is not usable there. Treat as best-effort trial.
- **IP-address certificates**: Let's Encrypt made these and 6-day ("shortlived", 160 h) certificates generally available on 2026-01-15. IP certs must use the `shortlived` profile and **only HTTP-01 and TLS-ALPN-01** validation (no DNS-01). Caddy/CertMagic support the profile (`issuer acme { profile shortlived }`); users report friction (for example caddy#7399). This gives a browser-trusted cert for a bare IP with no domain, usable with path-based routing.
- **Tenant resolution (what the edge must preserve):**
  - **Realtime**: tenant = first label of `Host` (`get_external_id/1` in `lib/realtime/database.ex`, per our audit in 04). `SELF_HOST_TENANT_NAME`/`SEED_SELF_HOST` only seed one default tenant.
  - **Storage**: in multitenant mode `src/http/plugins/tenant-id.ts` reads **`x-forwarded-host`** only, applies `REQUEST_X_FORWARDED_HOST_REGEXP` and takes `result[1]` (confirmed from the source). `Host` is ignored. A missing or non-matching header falls to the default tenant and fails.
  - **supabase-js**: builds `new URL('rest/v1', baseUrl)` etc. after `ensureTrailingSlash`, so a base URL with a path prefix (`https://host/p/<ref>/`) works. Caveat: the default auth storage key is `sb-<first hostname label>-auth-token`, so on a shared host (IP, or sslip.io with path routing) every project collides on one localStorage key unless the client sets `auth.storageKey`.

### 3.2 Options compared

|---|---|---|---|---|
| **Wildcard DNS + DNS-01 wildcard cert** (`*.api.<domain>`) | One wildcard A record (or none if the stack manages the Route 53 zone) + DNS API token (instance role on AWS) | One cert, renewed by `sbctl` | Yes, natively (first label = ref; regex like `^([a-z0-9]{20})\.api\.<domain>$`) | Best UX after setup; matches the hosted URL shape |
| **Wildcard DNS + on-demand HTTP-01 per ref** | Same wildcard A record, no API token | One cert per project at first request | Yes | 50/week per registered domain; seconds of first-request latency; needs port 80 open |

### 3.3 Proposed default **[ANALYSIS]**

1. **Default (production)**: `--domain example.com` gives `*.api.example.com` with a wildcard cert by DNS-01. Credential sources, in order: EC2 instance role (Route 53), then `--dns cloudflare|hetzner|digitalocean|route53 --token-file`.
2. **No DNS API access**: wildcard A record by hand plus on-demand HTTP-01 per project, authorized by `sbctl`'s project table. Document the 50/week ceiling.
3. **Zero-config trial**: `--sslip` gives `<ref>.api.<dashed-ip>.sslip.io` with on-demand HTTP-01; if issuance fails, `sbctl` serves HTTP and prints a warning.
4. **Compat mode (no domain, one IP)**: path-based routing with an LE IP certificate and Host rewrite, labelled experimental until tested against Realtime and Storage.
5. The edge always sets a **normalized** `Host` and `X-Forwarded-Host` for shared services in every mode, so Realtime and Storage see one shape.

## 4. Process supervision without Docker

### 4.1 Precedents

- **Debian/Ubuntu `postgresql-common`**: many clusters per host, each a `postgresql@<version>-<cluster>.service` template instance, managed by `pg_createcluster`/`pg_ctlcluster`. The closest ready-made precedent for `sb-postgres@<ref>.service`.
- **PocketHost** (own supervisor): launches a PocketBase instance just in time on the first request, hibernates it after **5 seconds** idle, and claims "dozens, hundreds, even thousands" of instances per server.
- **Supabase native stack** (`@supabase/stack` in the CLI): its own TypeScript orchestrator; services lazy-start and stop after **60 s idle** (Studio 5 min). Documented as local development only.
- **Neon** (the scale-to-zero bar): suspends compute after 5 minutes by default; cold starts reported at 300-500 ms.
- **Supabase's own ansible** (supabase/postgres): one project per VM. `postgresql.service` is `Type=notify`, `OOMScoreAdjust=-1000`, `Restart=always`, `LimitNOFILE=16384`, `TimeoutStopSec=90`, `KillMode=mixed`, `KillSignal=SIGINT`. `gotrue.service` sets `MemoryAccounting=true`, `MemoryMax=50%` and `Slice=services.slice`. PostgREST sets `Slice=services.slice` and `LimitNOFILE=100000`. **`services.slice` has no resource limits**: its file holds only a description ("used for general services grouping for easy visibility"). Supabase does not apply per-project cgroup limits in ansible; their isolation is the VM.

### 4.2 Cgroup v2 limits via systemd

- `MemoryMax` is the hard limit (invokes the OOM killer, "last line of defense"); `MemoryHigh` throttles and is the primary control; `CPUQuota=200%` means two cores; `TasksMax` caps processes/threads. The modern controls need the unified cgroup v2 hierarchy. `Delegate=` hands a subtree to a unit.
- **[ANALYSIS]** Per-project slice: `sb-<ref>.slice` (refs are 20 lowercase letters with no dashes, so systemd's dash hierarchy nests them under `sb.slice`) with `MemoryHigh`, `MemoryMax`, `CPUQuota`, `TasksMax`. Postgres, GoTrue and PostgREST for a project all use `Slice=sb-%i.slice`. Postgres `shared_buffers` is shared memory and counts toward the cgroup, so set `MemoryMax` above `shared_buffers` plus connection memory with headroom, or the OOM killer will hit the postmaster.

### 4.3 Memory and cold-start evidence

Published numbers for a cold PG 17 tarball start are sparse. The search turned up only generic statements (postmaster start "no more than a second or so" without recovery; idle backends about 1.5-5 MB each; Neon 300-500 ms). So I measured one on this machine.

**Local measurement, 2026-10-06 [not a Linux number]:**
- Binary: `postgres 17.11` from the Supabase CLI's cached slim-services artifact (`darwin-arm64`), Apple silicon, Darwin 25.x.
- `initdb`: 0.78 s. `pg_ctl -w start` (unix socket only, `max_connections=20`, `max_wal_size=64MB`): **0.20-0.21 s to ready**, the same at `shared_buffers` of 128 MB and 32 MB.
- Idle memory by macOS `footprint` (postmaster + 5 children): **about 20 MB at `shared_buffers=128MB`, about 15 MB at 32 MB**.
- **25 clusters** initdb'd in parallel, then started in parallel: all ready in **0.91 s**, 150 processes. I did not capture an aggregate memory figure for the 25.
- Caveats: empty cluster, no Supabase init scripts, roles, extensions or `shared_preload_libraries`; macOS accounting (`footprint` is dirty private memory, whereas Linux `RSS` double-counts shared memory and cgroup `memory.current` or PSS is the right number). Treat as an order-of-magnitude lower bound. **Re-measure on Linux with the real Supabase config (supautils, pg_net, pgsodium) before making sizing claims.**

### 4.4 Instances per host in practice

My sources contain no authoritative public density figure for Postgres. The evidence is indirect: Debian multi-cluster is an ordinary supported setup; PocketHost reports thousands of (much smaller) instances; Neon packs several VMs per Kubernetes node. Memory is dominated by `shared_buffers` and live connections, not by the six idle processes. **[ANALYSIS]** On a 4 GB VM expect single digits to low tens of *active* projects (each also runs GoTrue and PostgREST), with idle sleep (stop Postgres after N idle minutes, restart on the first request in about 0.2-1 s) multiplying density for dev and staging projects.

### 4.5 systemd units vs a built-in supervisor **[ANALYSIS]**

| | systemd template units | `sbctl` supervises children |
|---|---|---|
| Restart, ordering, journald, sandboxing, OOM policy | Free | Must reimplement |
| cgroup limits | Native | Must write cgroup files or call systemd anyway |
| Survives `sbctl` crash or upgrade | Yes: databases keep running | No, unless detached |
| Idle sleep / lazy start | `sbctl` calls `systemctl start` over D-Bus on first request | Natural |
| Portability | Linux with systemd only (not WSL1, some containers) | Anywhere |
| Observability | `systemctl status 'sb-*'`, `journalctl -u sb-postgres@<ref>` | Custom |

**Recommendation:** `sbctl` is one systemd service that renders per-project unit files (`sb-postgres@.service`, `sb-gotrue@.service`, `sb-postgrest@.service`, `sb-<ref>.slice`) and drives them over D-Bus. Keep a small built-in supervisor only as a fallback for hosts without systemd. Control-plane upgrades then do not restart tenant databases.

### 5.2 Recommendation **[ANALYSIS]**

- **AWS**: real S3 through the instance role (`STORAGE_S3_*` / `GLOBAL_S3_*`, bucket from the stack; objects use the `<tenant>/<bucket>/<key>` prefix per our audit). The same bucket, under another prefix, holds backups.
- **Own machine / simple VPS**: Storage `file` backend as the default. Backups = filesystem snapshot or restic/rsync of the storage directory, plus pgBackRest/wal-g to a **posix repository** instead of S3 (pgBackRest posix repos **[UNVERIFIED here]**).
- **Optional "I want an S3 endpoint locally" bundle**: Garage, run unmodified as a separate process (AGPL-3.0; do not link it; get legal review before redistributing in a product). Opt-in (`sbctl enable s3-local`), not part of the default install.
- **Open question**: whether Storage's S3-protocol endpoint (`S3_PROTOCOL_*`) works with the file backend in multitenant mode. Not verified; test before promising S3-protocol access on own-machine installs.

## Recommended install UX **[ANALYSIS]**

Design rules, from the recipe in section 1: one binary (`sbctl`), one `install.sh`, one config file (`/etc/sbctl/config.toml`, env overrides), one root-owned state directory (`/var/lib/sbctl`), systemd units, a **claim token** instead of "first visitor wins", SHA-256 verification of every download, an idempotent re-run that preserves secrets, and `sbctl self-update` (PocketBase style) with an optional systemd timer.

`install.sh` does: detect the OS (Ubuntu 22.04+/24.04, Debian 12+; refuse glibc below 2.35), create the `sbctl` user, download `sbctl` and verify its checksum, write the config, install units, start `sbctl`, and print the dashboard URL and claim token. `sbctl` then fetches the slim-services artifacts (`tar.zst`, checksum-verified) on first project creation.

### (a) AWS (8 steps)

1. Click the **Launch Stack** link in the README (opens CloudFormation quick-create in the chosen region).
2. Review prefilled parameters: `InstanceType` (default 2 vCPU / 4 GB), `DomainName` and `HostedZoneId` (both optional), `AdminEmail`.
3. Tick "I acknowledge this template may create IAM resources", then choose **Create stack**.
4. Wait about 5-8 minutes. UserData runs `install.sh`, writes the config, and requests the wildcard cert by DNS-01 with the instance role (or falls back to `<ref>.api.<ip>.sslip.io` when no zone is given). CloudFormation waits for `cfn-signal`.
5. Open the stack **Outputs**: the dashboard URL and a link to the generated Secrets Manager secret holding the one-time claim token.
6. Open the URL, paste the token, set the admin password (or passkey).
7. **Create project**: `https://<ref>.api.<domain>` plus the anon/service keys appear. The stack's S3 bucket is already wired for Storage and backups.
8. Done. Updates: `sudo sbctl self-update`, or change the stack's `Version` parameter.

Needs: an AWS account; optionally a Route 53 hosted zone (otherwise two manual DNS records or the sslip.io default).

### (b) VPS, Hetzner or DigitalOcean (7 steps)

1. Create a VM: Ubuntu 24.04, 2 vCPU / 4 GB. Optionally paste a `#cloud-config` snippet into User data (Hetzner and DigitalOcean both support it); it runs steps 3-4 for you.
2. DNS: add `A api.example.com` and `A *.api.example.com` pointing at the VM IP. Skip for a trial and use `--sslip`.
3. SSH in and run `curl -fsSL https://get.<project>.dev | sudo bash -s -- --domain example.com`. Add `--dns cloudflare --token-file ...` (or `hetzner`, `digitalocean`) for a wildcard cert; omit it for per-project on-demand certs.
4. The installer opens ports 80/443 (ufw), starts `sbctl`, and prints the dashboard URL and claim token.
5. Open the URL, enter the token, create the admin.
6. **Create project**: `https://<ref>.api.example.com` and keys.
7. Storage uses the local file backend; backups go to a local path or any S3 URL set in `config.toml`.

### (c) Own Linux machine (7 steps)

1. Run `curl -fsSL https://get.<project>.dev | sudo bash` (or a `.deb`/tarball plus `sudo ./install.sh`).
2. The installer asks "reachable from the internet?" If **no**, it selects **local mode**: hostnames `<ref>.api.localhost` (browsers resolve `*.localhost` to loopback; check glibc/systemd-resolved behavior **[UNVERIFIED]**) and a local CA from `sbctl trust` that adds the root to the OS/browser trust store. If **yes**, it asks for a domain and follows the VPS path.
3. It starts `sbctl` under systemd and prints `http://localhost:<port>` and the claim token.
4. Open the URL, enter the token, set the admin password.
5. **Create project**: local URL and keys. Postgres starts on demand (about 0.2 s measured cold start) and sleeps when idle.
6. Storage uses the file backend under `/var/lib/sbctl/storage`. Optional: `sbctl enable s3-local` (Garage) for an S3 endpoint.
7. For LAN or remote access, use a real domain (DNS-01 wildcard) or Tailscale. `tailscale cert` issues a cert for one name, not wildcards **[UNVERIFIED here]**, so use path-based compat mode there.
