# Supavise v0.2.1

v0.2.1 fixes two things a server that came from v0.1.x runs into. The upgrade now moves Studio when only its patches change, so Connect > MCP shows the server's own MCP URL and `api.<domain>/mcp` works. The AWS stack update now runs on stacks made in the CloudFormation console; v0.2.0 refused them.

## What this release fixes

### The upgrade moves Studio when only its patches change

On a server that upgraded from v0.1.3 to v0.2.0, Studio kept running the v0.1.3 build. Connect > MCP shows `http://localhost:8080/mcp`, and `api.<domain>/mcp` has no Studio route behind it. Both releases build the same upstream Studio tag. v0.2.0 adds patch 0004, which serves Studio's MCP route and gives the Connect panel its URL. The upgrade compared the upstream tag alone, so it saw no change and left the old build in place.

v0.2.1 names a Studio build by its upstream tag and its patch set, for example `2026.10.05-sha-94b8b06-p3`. The server uses that name for the build's directory, for the pin the upgrade plan compares, for the artifacts it keeps, and in the signed release manifest. A release that changes only the patches now moves Studio the way a new upstream tag does.

To fix an affected server, run `sudo supavise upgrade`. No other step is needed:

1. The plan lists Studio among the shared services that move.
2. Before anything stops, the new binary fetches the release's Studio build, checked against the signed checksum list.
3. The new daemon restarts Studio on that build, with the MCP URL.
4. `config.toml` then names the new build in `[studio] artifact_url` and `artifact_sha256`.

If the upgrade rolls back, Studio runs the previous build again. A rollback with `supavise rollback` also gives `config.toml` back the previous build.

A server installed fresh at v0.2.0 already runs the v0.2.0 build. Its plan also lists a Studio move. The upgrade reuses the build on disk instead of downloading it again, and Studio restarts once.

`supavise artifacts fetch --studio` without a service name now fetches Studio alone. To fetch every pinned artifact as well, run `supavise artifacts fetch` and then `supavise artifacts fetch --studio`.

### Upgrade a follower with a dashboard with `self-update` first

In a two-server cluster, run `sudo supavise self-update` on a follower that runs v0.2.0 or earlier and has a dashboard, then `sudo supavise upgrade`. Do not run `supavise upgrade` alone there, and set `[update] mode` back to `notify` on such a follower until it runs v0.2.1.

The reason is the old upgrade code. The upgrade to v0.2.1 is driven by the installed binary, so a follower on v0.2.0 runs v0.2.0's upgrade. That upgrade sees the Studio move and waits for Studio to run the new build. A follower keeps Studio stopped, so the wait ends after six minutes and the upgrade rolls back. `self-update` swaps the binary without that wait: the new binary fetches the Studio build from its own release and the follower keeps Studio stopped on it. The `supavise upgrade` after it then has no Studio move. From v0.2.1 on, the upgrade counts a stopped Studio on a follower as moved once its unit is set to run the new build. A leader and a single server are not affected.

### A Studio that stayed behind is repaired by `supavise upgrade`

`supavise self-update` fetches the new Studio build from the signed checksum list of the new binary's release. If it cannot (the server cannot reach GitHub, for example), Studio keeps running the build it ran. From v0.2.1 on, `supavise status` then names the build Studio runs and the build the release pins. Run `sudo supavise upgrade` to repair it: on the installed release, the upgrade fetches the build, restarts the daemon and waits until Studio runs the build. Projects keep running.

`sudo supavise system converge` also fetches a missing build, but it restarts nothing. Studio runs the build once `supavise.service` restarts.

Converge changes only `[studio] artifact_url` and `artifact_sha256` in `config.toml`, in place, and keeps the rest of the file, comments included. It changes them only when the URL names a release asset of another Studio build. A URL that names the installed build, or that names no build (a file name of your own), stays as you set it.

### Stacks made in the console were refused

A stack made in the CloudFormation console, or with the Launch Stack button, has an empty `AmiId`. Its instance image came from the template's `{{resolve:ssm:...}}` reference to the current Ubuntu image. AWS resolves that reference again on every update, so `supavise-aws-deploy.sh update` sets `AmiId` to the image the instance runs. CloudFormation can't tell before the update runs whether that image is the one the reference gives. The change set therefore said the instance may be replaced, and so may the volume attachment and the address association that refer to it. v0.2.0 refused that change set:

```
REPLACE  Instance (AWS::EC2::Instance) may be replaced: Tags, ImageId, MetadataOptions
10 change(s): 6 allowed, 4 refused, 0 blocked
```

A stack made with `supavise-aws-deploy.sh` was not affected, because the script always passes an image ID.

### The update now runs such a change set under a guard

The review has a fourth verdict, **guarded**, next to allowed, refused and blocked. A change is guarded when CloudFormation decides only while the change set runs whether a resource is replaced, and the possible outcomes are no change, a change in place that is known to be safe, or a replacement:

- a property that CloudFormation resolves while the change set runs, such as the image of a console-made stack;
- a property that can change only by a replacement, such as the image, whenever the change set doesn't mark its change as certain;
- a property that refers to a resource the change set may replace, such as the volume attachment and the address association;
- a change in place that comes only from such a reference, such as the data volume's `AvailabilityZone`.

A guarded change set runs under a temporary stack policy (the guard). The guard denies the replacement and the removal of every resource type in the stack except the ones the review already lets through: a security group rule, an IAM policy or a bucket policy. If CloudFormation decides while the change set runs to replace the instance or anything else the guard covers, AWS is expected to refuse it. The update then fails, CloudFormation rolls the stack back, and nothing is replaced. The script says so, names what a stack policy denied, and says what to do next. If the rollback doesn't finish, the script says that the state of the stack is not known and prints the command that resumes the rollback.

After the update ends, whether it succeeded or failed, the script puts back the stack's own policy. A stack that had no policy gets one that allows every update, because a stack policy can't be deleted.

### Interrupts and a guard that stays on

If you press Ctrl-C while a guarded update runs, the script says that the update goes on in CloudFormation, waits for it to end, and then takes the guard off. A second Ctrl-C leaves the guard on and prints the command that takes it off. `sudo -E supavise upgrade --aws` passes Ctrl-C and `TERM` on to the script instead of killing it, so the same holds on the node.

A guard can still stay on, for example when the script is killed or the session is lost. The next `update` finds it and takes it off before it does anything else, and `status` shows it with the command that takes it off. If the update succeeds but the guard can't be taken off, the script ends with exit status 4, and its last line says that the guard is on.

### What is still refused

- A replacement that the change set marks as certain (`Replacement: True`).
- A removal of anything other than a security group rule or an IAM policy.
- A change in place that the script doesn't know to be safe, such as `UserData` or `InstanceType`. This includes a change whose value CloudFormation resolves only while the change set runs, or that comes from a resource the change set changes in place. The guard can't stop a change in place.
- A new image: when the change set shows the instance's image before and after, and the two image IDs differ.

A change that would move the service address back after a failover is still blocked.

## Before you upgrade

- **New permissions.** Every update calls `cloudformation:GetStackPolicy` to find a guard that an earlier run left on; without it, the update skips that check. A guarded update also calls `cloudformation:SetStackPolicy`. `cloudformation:DescribeStackEvents` is optional: with it, a failed update names what failed.
- **Permissions for a rollback.** A guarded update can end in a rollback by design. The rollback deletes what the update added, so the credentials that update the stack need `iam:DeleteRole`, `iam:UntagRole`, `s3:DeleteBucket`, `s3:DeleteBucketPolicy` and `ec2:DeleteTags` as well. Without them, the stack can be left in `UPDATE_ROLLBACK_FAILED`. A console-made stack may also need `ssm:GetParameters` on the Ubuntu image parameters; that has not been checked. An administrator role, such as CloudShell's, has all of these.
- **`--allow-risky` sets no guard.** It still means that you accept replacements after you type the stack name. It now names the guarded resources that CloudFormation may replace, and says when the change set doesn't need the flag.
- **AWS CLI.** The script reads the change set with `--include-property-values` to show the image before and after, and runs it with `--no-disable-rollback`. An older AWS CLI doesn't know these options, and the script then goes on without them.

## Upgrade

1. On the server, run `sudo supavise upgrade`. That moves the binary and Studio.
2. On AWS, bring the stack forward with the script attached to this release, from CloudShell or anywhere with your AWS credentials:

```bash
bash supavise-aws-deploy.sh update --region <region> --stack <stack name>
```

On the node, `sudo -E supavise upgrade --aws` runs the same script. Its exit statuses are 0 updated, 2 refused and nothing changed, 3 failed, and, new in this release, 4 updated but the guard is still on, and 130 or 143 interrupted. A guarded update that CloudFormation rolled back ends with 3. On exit status 4, the node's upgrade goes on and says at the end that the guard is on.

## What has not been checked against AWS

The tests run the script against a stand-in for the AWS CLI, with bash 3.2 (macOS). These things have not run against a real stack yet:

- the change set details of a console-made stack, which the test fixtures model on the refused run above and on the AWS documentation (three shapes);
- the guard policy, which follows the documented stack policy grammar;
- whether CloudFormation enforces the stack policy for a replacement that it decides while the change set runs;
- whether the rollback of such an update finishes while the guard denies the removal of the resources the rollback deletes (the documentation says that a stack policy applies during updates and is silent on rollbacks);
- the wording of the event that a refused replacement leaves;
- the script on bash 5 (CloudShell).

`deploy/aws/rehearse.sh --console-stack` makes a throwaway stack the console's way, saves the change set AWS gives it, and updates it under the guard. Add `--force-denial` to check that the guard refuses a replacement and that the stack rolls back completely. Run it once before you update a stack you depend on.
