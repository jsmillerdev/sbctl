# Supavise v0.2.1

The AWS stack update now runs on stacks made in the CloudFormation console. With v0.2.0, the update refused such a stack, and nothing could bring it forward without `--allow-risky`.

## What this release fixes

### Stacks made in the console were refused

A stack made in the CloudFormation console, or with the Launch Stack button, has an empty `AmiId`. Its instance image came from the template's `{{resolve:ssm:...}}` reference to the current Ubuntu image. AWS resolves that reference again on every update, so `supavise-aws-deploy.sh update` sets `AmiId` to the image the instance runs. CloudFormation can't tell before the update runs whether that image is the one the reference gives. The change set therefore said the instance may be replaced, and so may the volume attachment and the address association that refer to it. v0.2.0 refused that change set:

```
REPLACE  Instance (AWS::EC2::Instance) may be replaced: Tags, ImageId, MetadataOptions
10 change(s): 6 allowed, 4 refused, 0 blocked
```

A stack made with `supavise-aws-deploy.sh` was not affected, because the script always passes an image ID.

### The update now runs such a change set under a guard

The review has a fourth verdict, **guarded**, next to allowed, refused and blocked. A change is guarded when CloudFormation decides only while the change set runs whether a resource is replaced, and the possible outcomes are no change, a change in place that is known to be safe, or a replacement:

- a property that CloudFormation resolves while the change set runs, such as the image of a console-made stack;
- a property that refers to such a resource, such as the volume attachment and the address association;
- a change in place that comes only from such a reference, such as the data volume's `AvailabilityZone`.

A guarded change set runs under a temporary stack policy (the guard). The guard denies the replacement and the removal of every resource type in the stack except the ones the review already lets through: a security group rule, an IAM policy or a bucket policy. If CloudFormation decides while the change set runs to replace the instance or anything else the guard covers, AWS refuses it, the update fails, CloudFormation rolls the stack back, and nothing is replaced. The script says so.

After the update ends, whether it succeeded or failed, the script puts back the stack's own policy. A stack that had no policy gets one that allows every update, because a stack policy can't be deleted. If the script is interrupted, it waits for the update to end before it takes the guard off. A second Ctrl-C leaves the guard on and prints the command that takes it off. If the policy can't be put back, the script prints a warning and that command.

### What is still refused

- A replacement that the change set marks as certain (`Replacement: True`).
- A removal of anything other than a security group rule or an IAM policy.
- A direct change in place that the script doesn't know to be safe, such as `UserData` or `InstanceType`, also when CloudFormation resolves its value only while the change set runs.
- A new image: when the change set shows the instance's image before and after, and the two image IDs differ.

A change that would move the service address back after a failover is still blocked.

## Before you upgrade

- **New permissions.** A guarded update calls `cloudformation:GetStackPolicy` and `cloudformation:SetStackPolicy` with your credentials. `cloudformation:DescribeStackEvents` is optional: with it, a failed update names the resource the guard refused. An administrator role, such as CloudShell's, has all three.
- **`--allow-risky` sets no guard.** It still means that you accept replacements after you type the stack name.
- **AWS CLI.** The script reads the change set with `--include-property-values` to show the image before and after. An older AWS CLI doesn't know that option, and the review then goes on without the values.

## Upgrade

Run the update as before, with the script attached to this release:

```bash
./supavise-aws-deploy.sh update --region us-west-2 --stack supavise-stack
```

On the node, `sudo -E supavise upgrade --aws` runs the same script. Its exit statuses are unchanged: 0 updated, 2 refused and nothing changed, 3 failed. A guarded update that CloudFormation rolled back ends with 3.

## What has not been checked against AWS

The tests run the script against a stand-in for the AWS CLI. Three things have not run against a real stack yet:

- the change set details of a console-made stack, which the test fixture models on the refused run above and on the AWS documentation;
- the guard policy, which follows the documented stack policy grammar;
- the wording of the event that a refused replacement leaves.

`deploy/aws/rehearse.sh --console-stack` makes a throwaway stack the console's way and updates it under the guard. Run it once before you update a stack you depend on.
