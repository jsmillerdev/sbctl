# Supavise v0.2.0

A second server joins the first for read replicas and failover, upgrades bring existing servers and AWS stacks forward, and MCP clients sign in to your server with OAuth.

This release adds registry migrations. Read "Before you upgrade" first.

## What this release adds

### Read replicas and failover

- **A second server.** `supavise node token` on the first server and `supavise install --join-token-file` (or `supavise node join`) on the second join them over one encrypted port. The second server keeps a copy of the registry ([guide](../guide.md#read-replicas-and-failover)).
- **Read replicas per project,** through Studio's replica screens and the Management API (`read-replicas/setup` and `/remove`). Each replica has its own API and pooler endpoints, and a load-balancer host sends Data API reads to replicas. `[replicas] default = "all"` gives every project a replica.
- **Failover.** `supavise projects failover <ref>` moves one project and `supavise failover` moves the whole server, planned or unplanned; `supavise node rejoin` brings the old server back as a follower. Automatic failover on AWS fences the failed instance before it promotes.
- **Storage on S3.** `supavise storage migrate --to s3` moves Storage's files to a bucket in place, with a pause of a few seconds for writes.
- **Upgrades bring everything forward.** `supavise system converge` brings the host up to date, and `supavise upgrade --aws` updates an AWS stack through a change set that refuses to replace the instance, its volume or its address. `supavise-aws-deploy.sh --delete --purge` removes a stack and everything it kept.

### OAuth sign-in for MCP clients

A person adds `https://api.<domain>/mcp?project_ref=<ref>` to Claude Code, Cursor, VS Code, Codex or the Claude desktop connector and approves the client in Studio. No personal access token is needed.

- **OAuth sign-in for MCP clients.** The Management API is the OAuth 2.1 authorization server: discovery documents, dynamic client registration, authorize, token and revoke. `api.<domain>/mcp` is the protected MCP endpoint. Studio's Connect > MCP panel shows the URL, and Studio's "Authorize API access" page asks an Owner or Administrator to approve a client for one organization.
- **The organization's OAuth Apps page works.** It lists the clients that have access, revokes them, and publishes your own apps with client secrets.
- **`supavise oauth grants list` and `supavise oauth grants revoke`** show and end grants from the server, by user, organization, app or all at once.
- **A fourth Studio patch.** Patch 0004 makes Studio's own MCP route work in platform mode, so the hosted tool set is available behind the endpoint. It is specific to Supavise and is not proposed upstream ([design, section 13.5](../design.md#135-studio-patch-0004)).
- **`[api] disable_oauth`.** Setting it to `true` turns all of this off.

## Before you upgrade

- **Migrations 1300 and 1301 add the cluster and replica tables, and 1350 adds five OAuth tables** (`oauth_apps`, `oauth_app_secrets`, `oauth_grants`, `oauth_authorizations`, `oauth_tokens`). None changes an existing table. Migrations only go forward, so after the upgrade `supavise rollback` refuses until you restore the system cluster from its pre-upgrade base backup, as [the deploy guide](../../deploy/README.md#upgrading-the-node-supavise-upgrade) describes. `supavise upgrade` takes that backup first.
- **An AWS stack:** run `deploy/aws/rehearse.sh` on a throwaway stack made from the v0.1.x template before `supavise upgrade --aws` updates the stack you depend on. Automatic failover on AWS has been tested against a simulated EC2 API, not on AWS itself.
- **Upgrade as usual** with `sudo supavise upgrade`. The binary and the Studio build move together. If only one of them is current, the Connect panel shows the old local URL or `/mcp` has nothing to forward to; both resolve when the other catches up.
- **Existing access is unchanged.** Personal access tokens and dashboard sessions work as before. OAuth tokens are stored in their own tables, so a release without OAuth answers 401 for them and never treats one as a personal access token.

## What to know after you upgrade

- **Who approves.** Owners and Administrators, for one organization at a time. A client acts with the approver's current role in that organization, limited to the scopes it asked for. A role change applies at once.
- **Lifetimes.** An access token lasts 1 hour. A refresh token lasts 90 days and each use renews it.
- **Registration is open,** as on hosted Supabase: any client that can reach `api.<domain>` can register. A registered client gets nothing until an Owner or Administrator approves it on a page that shows its name, redirect host and scopes. Registration is limited per client address, and every approval is an audit event.
- **Documentation search** (`search_docs`) calls `supabase.com` from your server, as on hosted Supabase.
- **The endpoint is stateless.** It accepts `skip_elicitations` and ignores it, and a tool that asks the client to confirm a cost (`create_project`, `create_branch`) cannot ask. A client that speaks only a newer MCP protocol revision than the endpoint's SDK supports may not connect.
- **`get_project_url`** is correct through `/mcp`. The stdio MCP server, started with `--api-url`, still derives a `supabase.red` address for any host that is not hosted Supabase.
- **Limits are per node.** In a two-server cluster each server counts its own registrations, authorizations and requests.
