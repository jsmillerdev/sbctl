- Latest PG17 extension versions in the source tree (`supabase/postgres` `nix/ext/versions.json`): pg_graphql 1.6.2, pg_net 0.20.4, pg_cron 1.6.4, pgsodium 3.1.8, supabase_vault 0.3.1, vector 0.8.2, wrappers 0.6.3, pgaudit 17.1, postgis 3.3.7, pgmq 1.5.1, pg_partman 5.3.1, pg_tle 1.4.0, pgroonga 3.2.5, rum 1.3, safeupdate 1.4, pg_jsonschema 0.3.3, hypopg 1.4.1, http 1.6.1. Slim ships "latest-only" of each (`latestOnly = true`), not the historical version stack the full image carries.
- Roles/migrations: the launcher runs upstream `supabase-postgres-init.sh` (initdb with the docker.io flags: `--allow-group-access --locale-provider=icu --encoding=UTF-8 --icu-locale=en_US.UTF-8`), then starts a temporary socket-only server and runs the bundled `share/supabase-cli/migrations/migrate.sh` (from `supabase/postgres/migrations/db/`), then optional `SUPABASE_POSTGRES_INITDB_DIR` files, then removes the pending witness (`.supabase-postgres-init-pending`) as the commit point and execs the final server. A failed first boot fails closed on later starts. `pgsodium.getkey_script`/`vault.getkey_script` come from `share/supabase-cli/config/pgsodium_getkey.sh`; the CLI feeds `PGSODIUM_KEY_FILE`.
- Launcher env: `PGDATA`, `POSTGRES_USER` (default `supabase_admin`), `POSTGRES_PASSWORD` (default `postgres`), `POSTGRES_DB`, optional `SUPABASE_POSTGRES_CONFIG_DIR`, `SUPABASE_POSTGRES_INITDB_DIR`, `SUPABASE_POSTGRES_SCHEMA_FILE`, `SUPABASE_POSTGRES_SCHEMA_BACKUP`.

Deliberate divergences (all in `local-dev.conf`): loopback + port 54322, `/tmp` socket, `shared_buffers=32MB`, `effective_cache_size=128MB`, `maintenance_work_mem=32MB`, `max_wal_size=128MB`, `jit=off`, slowed autovacuum/bgwriter/wal_writer ticks; `max_connections=100`; `wal_level=logical` left alone. One security-relevant divergence: `pg_hba` `peer map=supabase_map` is replaced with `trust` for local, and the CLI writes its own HBA that trusts `supabase_admin` (packages/stack/README.md "Native PostgreSQL listens only on its socket ... trusts `supabase_admin`"). Upstream also sets `max_wal_senders=0` for parity, so physical replication needs reconfiguration.
- **PgBouncer: not shipped.** Only `ansible/files/pgbouncer_config/pgbouncer_auth_schema.sql` is added (the `pgbouncer` schema/auth function). **wal-g: not shipped.** Only `custom_walg.conf` (archive/restore commands commented out, referencing `/usr/bin/admin-mgr`) is staged as `wal-g.conf`. Neither is in the upstream Docker image's Nix package set either (`Dockerfile-17` creates a `wal-g` user and copies helper scripts but installs no wal-g binary). A backup story (pgBackRest, wal-g) is ours to supply.
- Client tools in `bin/`: `psql`, `pg_dump`, `pg_dumpall`, `pg_restore`, `pg_isready`, `pg_prove` (TAP::Harness).

### 1.5 How `@supabase/stack` wires processes

Location: https://github.com/supabase/cli/tree/main/packages/stack (`ARCHITECTURE.md` 860 lines, `README.md` 223 lines). `package.json`: `"name": "@supabase/stack"`, `"private": true`, `exports` point at `./src/*.ts` (raw TypeScript). Deps: `effect` (v4 rc), `@effect/platform-node`, `@effect/sql-pg`, `jose`; tests run under Bun/vitest. Repo license: MIT (GitHub API).

- **One detached owner per stack identity** (`StackHost.ts`): hosts per-service executors, the orchestrator, the proxy, the command runner. Control API is Effect RPC over loopback HTTP (`/identity`, `POST /shutdown`, `/rpc`; bound `127.0.0.1:0` at `StackHost.ts` L83). Lease = SQLite write transaction on `<stateRoot>/<id>/owner.lock`, held for the owner's lifetime (OS releases on exit).
- **State dir**: `<stateRoot>/<id>/state.json` (definitions, composition, credentials, sticky ports), service data under `<stateRoot>/<id>/data/<instance-id>`, logs under `<stateRoot>/<id>/logs`, `owner.log`; artifacts in a shared `cacheRoot`. Only normal stop/start state is persisted; health and transitions are not. Unexpected owner death kills native children (process-group + pipe lifeline) and the next owner sweeps orphans.
- **Port allocation** (`Ports.ts`): sticky claims recorded in saved state; "auto" scans from a hash of `projectRoot:stackId:key` across `portBase = 20000`, `portSpan = 12768` with stride 257 (below the Linux ephemeral range); probes loopback `127.0.0.1` and `::1` with a 250 ms connect timeout; an occupied saved port is reported as a conflict rather than moved. The CLI default also advertises 54321 (API), 54322 (DB), 54323 (Studio), 54324 (Mailpit) in docs.
- **Proxy** (`Network.ts`, `HttpProxy.ts`, `Proxy.ts`, `host/Endpoints.ts`): one shared HTTP listener built on `node:http` with a route table of `{prefix -> upstreamPrefix, target, keyRewrite}`; hop-by-hop headers stripped; WebSocket `upgrade` handled with raw sockets; only safe bodyless requests (GET/HEAD/OPTIONS/TRACE) are replayed on a connection reset; optional API-key rewriting (`sb_publishable_`/`sb_secret_` keys to the stack's anon/service_role JWTs for `bearer`, `query`, `sb-api-key` policies). Routes include `/realtime/v1/api`->`/api`, `/realtime/v1`->`/socket`, `/storage/v1/s3`, `/rest/v1`, `/auth/v1`, `/functions/v1`, `/mcp`->`/api/mcp`. Non-HTTP endpoints (Postgres SQL, pooler) get a dedicated TCP listener with a byte-copying proxy (`Proxy.ts` `serveTcp`). The `target` is an Effect that performs the orchestrated wake and returns `{host,port}` or `{path}` (unix socket supported as a backend address).
- **Lazy start / idle sleep** (`ARCHITECTURE.md` section 5, `composition/Supabase.ts` L10-L14): public traffic through the proxy is the only activity signal; a request or open stream counts, idle keep-alive does not. Defaults: `DEFAULT_IDLE_MILLIS = 60_000`, Studio `300_000`. Sleep = ordinary stop plus an armed wake route; data and port assignments are retained. Wake starts the dependency closure, waits for health, then forwards. Sleep is blocked while a dependent runs. Explicit stop disables wake. No auto-restart, no self-healing: "a crashed service stays stopped until explicit start/restart".
- **Native process mechanics**: `runtime/NativeProcess.ts` + `native-launcher.ts` (process-group stop, graceful signal/timeout: Postgres `SIGINT`, 15 s). Dependency ordering lives in composition, not recipes; readiness is observed separately from "running".
- **Native Postgres user handling**: refuses to run as uid 0; in detected agent sandboxes or with `SUPABASE_NATIVE_POSTGRES_USER=<name>` it drops privileges for the Postgres process only.

Reusability verdict: **take as reference, not as a dependency.** Reasons: not published (`private: true`), raw-TS exports, Effect v4 release candidate, CLI-coupled defaults (`DEFAULT_LOCAL_JWT_SECRET`, shared local credentials, Mailpit, Vector/Logflare wiring), single-project assumption (one stack = one project = one owner process), no per-tenant host routing (routes by path prefix on a loopback listener). Patterns worth copying: the lifecycle/health split, intent-revision race handling, lease via SQLite lock, sticky port ledger, wake-on-connect for TCP, content-pinned artifact store with mirror fall-through (`preparation/ArtifactStore.ts`, `Integrity.ts`), and the slim `bin/prepare` convention for one-shot migrations.

### 2.2 Is Turso's server open source and self-hostable multi-tenant?

Repos (GitHub API, 2026-10-06):
- `tursodatabase/turso`: MIT (`LICENSE.md`), v0.8.2 (2026-10-06), 24.6k stars, README: "an in-process SQL database written in Rust, compatible with SQLite. It runs in production today at multiple organizations." Not at 1.0 ("we have not yet reached 1.0"). Features: `BEGIN CONCURRENT` (MVCC), CDC, io_uring, vectors; experimental: Postgres dialect and wire protocol, encryption at rest, FTS (tantivy), incremental views, multi-process WAL (`.tshm`). Languages: Rust, JS/WASM, Python, Go, Java, .NET. Sync engine in `sync/engine` + `sync/sdk-kit` (client side).
- Server story in this repo: `tursodb --sync-server <addr> [--sync-dir <path>] [--sync-max-databases N]` (`cli/app.rs` L83-L101, `cli/sync_server.rs` 1642 lines, `cli/sync_server.mdx` calls it "local-sync-server", "simple implementation", generated from a spec prompt). `--sync-dir` serves every database under a directory at `/db/{name}/v2/pipeline` and `/db/{name}/pull-updates`; databases are created on first request; names `^[a-z0-9_-]+$` max 128 chars. The docs' own warning (`docs/sql-reference/cli/command-line-options.mdx` L156): "Directory mode handles one request at a time across all databases ... at most `--sync-max-databases` may be open at once (default 256) ... Any client that can reach the port can create a database ... `VACUUM INTO` can write a copy to any path ... There is no authentication or multi-tenancy; directory mode is intended for local and development use." `sync_server.rs` contains zero references to authorization/bearer/jwt/token.
- `tursodatabase/libsql`: MIT, fork of SQLite; contains `libsql-server` = `sqld` (binary `sqld`, crate 0.24.33). Capabilities from `docs/USER_GUIDE.md` and `docs/ADMIN_API.md`: HTTP (Hrana) + gRPC, primary/replica replication with TLS, `--enable-namespaces` with an admin API on `--admin-listen-addr` (`POST /v1/namespaces/:ns/create`, `DELETE`, `POST .../fork/:to`), client auth via `--auth-jwt-key-file` (Ed25519). Maintenance state: last GitHub release `libsql-server-v0.24.32` on 2025-02-14; only commits touching `libsql-server` since are a 2025-12 fsync fix and a 2026-05-14 doc typo. README: "libSQL is actively maintained, but new features are being developed in Turso." and the Turso README says the Rust rewrite "replaces libSQL as our intended direction". Per-namespace auth, tenant limits, and embedded-replica sync against namespaces: not verified here.
- Turso Cloud's multitenant server ("designed to host millions of SQLite files per node", WAL in S3 Express One Zone, BYOC for Pro/Enterprise): described in blogs, **not found** as open-source code in `github.com/tursodatabase` (`turso-cloud` repo is an issue tracker: "The public repository for Turso Cloud to track feature requests and bug reports"). BYOC is a commercial managed offering.
- Embedded replicas: libSQL feature (README) and Turso's newer sync protocol (`@tursodatabase/sync`, `sync/` dir); both clients, not a server multi-tenancy answer.

Bottom line: today you can self-host (a) the engine as a library/CLI under MIT, (b) `sqld` with namespaces + JWT (works, but in maintenance), or (c) the `--sync-dir` server for dev only. There is no OSS equivalent of the Turso Cloud "one server, millions of databases, S3-backed" tier.

### 2.3 Compute, Multigres, agents

- **Supabase Compute** (https://supabase.com/blog/select-2026-build-anything): "runs web services and agents in any language next to your database. There's no limit on how long a service runs, you choose the memory and CPU, and each service gets a full Linux environment, which Edge Functions don't have." Deploy via CLI/Management API; service definition in `config.toml`; public HTTP URL or private (no HTTP endpoint) "for background jobs from a database queue or as a sandbox for an agent"; multiple instances load-balanced; same default env vars as Edge Functions; network restrictions can limit DB access to Compute instances. "Private alpha. Join the waitlist." No repo or license found; no OSS statement. It is a long-running service host, not a database unit. SiliconAngle claims Turso technology "will enhance" Compute; Supabase's posts do not say this.
- **Multigres** (https://github.com/multigres/multigres): Apache-2.0, "Vitess for Postgres"; v0.1.0 released 2026-05-30 (blog "Multigres v0.1 Alpha", 2026-06-04: "open-source-only release"); alpha, "not yet ready for production workloads", v0.1 is single-shard HA + pooling, Kubernetes operator, pgBackRest backups, API not stable. On the platform: private alpha (Select recap), "built for testing during the alpha, not production workloads". Architecture: `multigateway` + `multipooler` + `multiorch` + `pgctld` (+ etcd topology). `supabase/postgres` already carries `Dockerfile-multigres` and `nix/packages/pgctld.nix`, and tags `17.*-multigres`.
  - Relevant to us: `docs/general/minigres.md` documents **Minigres**, "a multigateway and a multipooler in one process, for a database served by a single pooler with no replicas and no shards", still needs etcd and a separate `pgctld` process, started by hand (no provisioner yet), config files unsupported. This is the closest thing to a lightweight per-database pooler/control unit and a candidate Supavisor replacement later, but it is alpha and heavier (etcd) than Supavisor today.
- **Agents / ephemeral**: Series F post (2026-06-04): "database launches on Supabase have grown 600%. More than 60% of new databases are launched by some sort of AI tool." and "Supabase for Platforms has been the fastest growing product". Select posts: MCP Elicitations, Agent prompts, query_logs tool, supabase agent plugin. **Branching 2.0** is not new: https://supabase.com/blog/branching-2-0 is dated 2025-07-16 (public alpha; branches "a copy of your Supabase project, minus the data"). No Supabase statement found about "database-per-agent" or "ephemeral projects" beyond the Turso posts and Supabase for Platforms mentions; no hint of a per-project lightweight Postgres compute unit. Select recap notes Database Connections view is "On by default for every project, including self-hosted".

Does either hint at a per-project lightweight compute unit to design toward? Only indirectly: (1) Turso's "single server, millions of databases, load on demand, suspend when idle" is a per-database lazy-load pattern at the file level, which the Turso post pairs with a "graduation path" to Postgres; (2) Minigres is a one-process-per-database gateway+pooler; (3) the CLI stack's lazy-wake/idle-sleep owner is the process-level analog for Postgres. None of the three is announced as a hosted per-project unit.

## 4. Postgres extension and artifact parity

- Upstream extension list: `supabase/postgres` `nix/packages/postgres.nix` `ourExtensions` (31 entries: rum, timescaledb, pgroonga, index_advisor, wal2json, pgmq, pg_repack, pg-safeupdate, plpgsql-check, pgjwt, pgaudit, postgis, pgrouting, pgtap, pg_cron, pgsql-http, pg_plan_filter, pg_net, pg_hashids, pgsodium, pg_graphql, pg_stat_monitor, pg_jsonschema, pg_partman, pgvector, vault, hypopg, pg_tle, wrappers, supautils, plv8), filtered for PG17/OrioleDB-17 to drop timescaledb and plv8; OrioleDB adds `orioledb`. `ansible/vars.yml` only holds `postgres_major: ["15","17","orioledb-17"]` and releases `postgres17: 17.11.0.004`, `postgres15: 15.19.0.004`, `postgresorioledb-17: 17.11.0.004-orioledb` plus admin binaries (adminapi, admin-mgr, envoy 1.28.0, kong 2.8.1, gotrue 2.190.0, postgrest 14.18, ...); extension versions live in `nix/ext/versions.json`.
- Docker image build (main today): `Dockerfile-17` / `Dockerfile-15` / `Dockerfile-orioledb-17` ("Alpine-based slim PostgreSQL 17 image with Nix extensions") run `nix profile add path:.#psql_17_slim/bin` where `psql_17_slim = makePostgres "17" { latestOnly = true; }` (`nix/packages/postgres.nix` L238-L241). A separate `Dockerfile-multigres` builds the `-multigres` variants.
- Upstream also defines its own `psql_17_cli_portable` (`nix/packages/postgres-portable.nix`), but that upstream CLI variant is **minimal**: extensions `supautils, pg_graphql, pgsodium, supabase_vault, pg_net, pg_cron, safeupdate` (`cliExtensions`, receipt in the same file).
- slim-services does **not** consume that minimal upstream package. It re-implements `postgres.nix`/`postgres-portable.nix` in `services/postgres/nix/packages/` (885-line portable wrapper), importing upstream's `nix/ext/*.nix` expressions via `extensionRoot = "${upstream}/nix/ext"`, with the full `ourExtensions` list, `latestOnly`, bundled glibc loader, and relocation fixups. REPORT: "no upstream portable package is consumed".
- So: **same extension Nix expressions and same `ansible/files` config, same source commit, but a different final derivation than the Docker image's `psql_17_slim`.** Identical behavior is asserted by test, not by identity: `services/postgres/REPORT.md` "Differential docker.io parity smoke" boots the digest-pinned docker.io image beside the slim image and requires equal `pg_settings`, `pg_dumpall --globals-only`, schemas of `postgres`/`template1`, `pg_available_extensions`, encodings/locales, and `pg_hba_file_rules`, minus an explicit allowlist (local-dev GUCs, paths). Caveat: that REPORT describes the docker.io baseline as built from `Dockerfile-supabase`; current `supabase/postgres` main has no such file (Dockerfile-15/17/orioledb-17/multigres), so the parity harness's baseline recipe may have drifted. I did not run the smoke. If exact parity matters (pg_upgrade, replicas), pin and re-run it for the specific tag.
- Other differences to expect (from the files read): the Docker image wraps Nix-store binaries in an Alpine base with `gosu`/`su-exec` user handling, while the slim artifact bundles its own glibc loader and relies on a launcher that sets `LOCALE_ARCHIVE` to a bundled `en_US.UTF-8` archive; native mode has no entrypoint user switching; local-dev tuning in `local-dev.conf`.

## How a Turso/file-DB tier would slot into a multi-project control plane (analysis - mine, not sourced)

Premises (sourced above): Turso Database is an in-process engine (MIT, pre-1.0, MVCC concurrent writes, Postgres dialect experimental); its OSS server mode is dev-only (no auth, single request at a time, 256-DB cap); `sqld` has namespaces + JWT but is in maintenance; Turso Cloud's multitenant S3-backed server is proprietary; Supabase says a "clear path" from SQLite to Postgres exists but has published no mechanism, timeline, or self-host story.

1. Model "database kind" as a first-class project attribute from day one. Project spec: `engine: postgres | file`, plus `class: dedicated | pooled`. Control-plane state (project id, tenant keys, quotas, JWT secrets) stays engine-agnostic; only the "data plane unit" differs. This lets Postgres projects use per-project Postgres+GoTrue+PostgREST host processes (the `@supabase/stack` shape) while file projects need no per-project process at all.
2. File tier = shared data-plane service, one process, many files, like Supavisor/Realtime/Storage in the same design. Host: one `tursodb --sync-server --sync-dir /var/lib/files/<tenant-shard>/` (or `sqld --enable-namespaces`) per shard, with a data layout `<root>/<project-id>/<db-name>/data`. Turso's own layout is `dbs/<name>/data` with `-wal`/`-shm` siblings, which maps directly onto per-project directories and onto per-project backup/restore (copy directory while quiesced).
3. Put authn/z and quotas at the edge, not in the engine. Because Turso's directory mode has no auth, create-on-first-request, `VACUUM INTO`/`ATTACH` path escape, and global serialization, the Envoy tier must: validate a per-project JWT (the same project JWT secret GoTrue uses), rewrite `/files/v1/<db>/...` to `/db/<project-id>__<db>/...` (lowercase `[a-z0-9_-]{1,128}` constraint), deny creation via a control-plane-only admin path (pre-create files; return 404 for unknown names), forbid `--experimental-attach`, run the process as an unprivileged user in a chroot/namespace with disk quota (inode and size per project), and rate-limit. `sqld` + `--auth-jwt-key-file` is the alternative, but its single instance-wide key and maintenance status make it a weaker long-term bet; verify per-namespace auth before choosing it.
4. Single-request-at-a-time is a hard scaling limit: shard by process, not just by directory. Run N file-tier processes (control plane assigns `project -> shard`), each with a bounded open set, with the same lazy-start/idle-sleep owner pattern as the stack's proxy (start the shard process on first request; the stack README's wake-on-connect model fits a request/response HTTP workload well). Expect to revisit once Supabase/Turso publish a real multi-tenant server; keep the shard assignment table in the control plane so the backing implementation can change.
5. Graduation path (SQLite -> Postgres) is a control-plane operation, not an engine feature. Define it as: freeze writes at the edge (HTTP 503 with Retry-After), export (`tursodb` dump or logical copy), import into a new per-project Postgres from the slim artifact, flip `engine` in control-plane state, and repoint the edge route. Do not promise schema translation beyond what Turso's Postgres frontend/SQLite dialect actually support (Turso's Postgres compatibility is marked experimental). Supabase's "graduation path" language is a product intent; no tool exists to copy.
6. Do not couple the control plane to Turso's wire/sync protocol yet. Keep the file tier behind a narrow internal interface (`create(db)`, `delete(db)`, `snapshot(db)`, `route(db) -> backend`, `usage(db)`). The sync protocol (`/v2/pipeline`, `/pull-updates`) is documented (`serverless/PROTOCOL.md`, `cli/sync_server.mdx`) and clients exist (`@tursodatabase/sync`, libsql clients), so embedded/local-first replicas can talk to the edge route if we choose to expose it.
7. Treat Postgres-per-project and file-per-project as different cost curves in the control plane: per-project Postgres from the slim artifact costs ~80-100 MB RSS idle plus Auth/PostgREST (~12 + ~9 MB measured idle, manifests) and benefits from the stack's idle-sleep; the file tier costs ~0 for an idle project (file on disk). A "default to file, promote to Postgres" policy only makes sense if the control plane owns the promotion trigger (size, concurrency, features such as RLS/extensions), because Supabase has not defined one.
8. Multigres/Minigres is the later HA/pooler story, not the file tier. If per-project Postgres needs a pooler better than Supavisor (which has no bind-IP knob and a wildcard bind), Minigres is the candidate, but it needs etcd and is alpha; keep Supavisor as a shared service behind Envoy for now and treat Minigres as a swap-in behind the same SQL listener.
9. Risks to record: Turso pre-1.0 file-format/engine churn ("we have not yet reached 1.0"), possible relicensing or product reshaping after the acquisition (nothing announced; MIT today), and no OSS multi-tenant server. Pin the Turso version per shard; keep daily snapshots independent of Turso features.
