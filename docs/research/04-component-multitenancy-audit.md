## 1. Supavisor (github.com/supabase/supavisor)

**Verdict: native multi-tenant, runtime-managed, the cleanest building block for shared infrastructure.** [code]

**Architecture (README.md, "Architecture"):** tenant config lives in a highly available Postgres database and is loaded when a tenant's pool is first started; pools are dynamic (started when the first client for that tenant connects), pool pids are distributed across cluster nodes via an in-memory registry, and only one pool per tenant lives in a cluster so upstream connection counts stay at `default_pool_size`. Features list: "Multi-tenant - connect to multiple different Postgres instances/clusters", "Single-tenant - drop-in replacement for PgBouncer", Prometheus `/metrics`, OpenAPI at `/api/openapi`, Swagger UI at `/swaggerui`. Claimed scale: 1,003,200 client connections on a 2-node 64 vCPU cluster; 250,000 idle connections on one 16-core/64 GB node.

**Tenant identification** (`docs/connecting/overview.md`; `lib/supavisor/handler_helpers.ex#parse_user_info`):
1. Username: the `external_id` is everything after the **last** dot: `postgres.<external_id>`. `.cluster.` in the username switches to cluster mode (alias).
2. TLS SNI: the subdomain of the SNI hostname.
3. Startup `options` parameter: `options=reference%3D<external_id>`.
Tenants can also match by `sni_hostname` on the tenant record.

**Where config is stored:** Postgres schema `_supavisor` (`@schema_prefix "_supavisor"` in `lib/supavisor/tenants/{tenant,user,cluster,cluster_tenants}.ex`). In the official self-host compose it lives in database `_supabase` (`volumes/db/_supabase.sql`: `CREATE DATABASE _supabase`, `volumes/db/pooler.sql`: `create schema _supavisor`). Compose runs `/app/bin/migrate && /app/bin/supavisor eval "$(cat pooler.exs)" && /app/bin/server`; `volumes/pooler/pooler.exs` seeds exactly one tenant (`POOLER_TENANT_ID`) via `Supavisor.Tenants.create_tenant/1`. Metadata DB can be any Postgres: `DATABASE_URL` (default `ecto://postgres:postgres@localhost:6432/postgres`), `DB_POOL_SIZE` 25.

**Tenant record fields** (`lib/supavisor/tenants/tenant.ex`, `docs/configuration/tenants.md`): `external_id`, `db_host`, `db_port`, `db_database`, `ip_version`, `upstream_ssl`, `upstream_verify` (`none|peer`), `upstream_tls_ca`, `enforce_ssl`, `require_user`, `auth_query`, `default_pool_size` (default 15), `default_max_clients` (default 1000), `client_idle_timeout`, `client_heartbeat_interval` (60), `allow_list` (CIDR list), `sni_hostname`, `default_parameter_status`, `availability_zone`, `feature_flags` (e.g. named prepared statements per tenant), JIT fields (`use_jit`, `jit_api_url`), ban fields (`banned_at`, `ban_reason`, `banned_until`).
**User record** (`user.ex`): `db_user_alias`, `db_user`, `db_password` (encrypted with `VAULT_ENC_KEY` via Cloak; column `db_pass_encrypted`), `is_manager`, `mode_type` (`transaction|session`), `pool_size`, `pool_checkout_timeout` (60 s), `max_clients`.

**Authentication of clients:** `docs/connecting/authentication.md`: either per-tenant `user` rows (`require_user`) or an `auth_query` run through the tenant's `is_manager` user against the tenant DB. The compose seed uses `auth_query = SELECT * FROM pgbouncer.get_auth($1)` with user `pgbouncer`, which means the upstream DB must carry the `pgbouncer` role and `pgbouncer.get_auth` function. Both ship in the `supabase/postgres` image (`ansible/files/pgbouncer_config/pgbouncer_auth_schema.sql`).

**Management API** (`lib/supavisor_web/router.ex`; pipeline `:api` -> `check_auth([:api_jwt_secret, :api_blocklist])`): HS256 Bearer token verified against `API_JWT_SECRET` (blocklist `API_TOKEN_BLOCKLIST`; `JWT_CLAIM_VALIDATORS`). Routes:
- `GET/PUT/PATCH/DELETE /api/tenants/:external_id` (PUT = create-or-update; body `{"tenant": {..., "users": [...]}}`, see `TenantCreate` schema in `lib/supavisor_web/open_api_schemas.ex`)
- `GET /api/tenants/:external_id/terminate` (stop pools and clear cache)
- `POST /api/tenants/:external_id/update_auth_credentials`
- `GET/DELETE /api/tenants/:external_id/network_bans`
- `GET /api/health` (unauthenticated), `POST /api/rebalance`
- `GET/PUT/DELETE /api/clusters/:alias` (cluster = group of tenants typed `write`/`read`, `ClusterTenants`).
Metrics: `GET /metrics` (all, cluster-aggregated) and `GET /metrics/:external_id` (per tenant), Bearer JWT signed with `METRICS_JWT_SECRET`.

**Pool modes:** `docs/configuration/pool_modes.md` lists `transaction`, `session`, `native`; the `Ecto.Enum` on `user.mode_type` only accepts `transaction|session`, and the actual listener is selected by port: `lib/supavisor/application.ex` starts `:pg_proxy_transaction` on `PROXY_PORT_TRANSACTION` (6543) and `:pg_proxy_session` on `PROXY_PORT_SESSION` (5432) (`config/runtime.exs`). Treat mode as port-selected [code]. The README feature list says "Pool mode support per tenant - Transaction" (stale vs docs).

**Cluster mode:** `CLUSTER_POSTGRES=true` (node discovery through the metadata DB; set in the official compose), `CLUSTER_NODES`, `DNS_POLL`, `NODE_NAME`, `NODE_IP`, `REGION`, `AVAILABILITY_ZONE`. Erlang distribution; `RELEASE_COOKIE` random by default. Rolling and hot upgrades supported (`relups/`, `lib/supavisor/hot_upgrade`).

**Hosted platform use:** the Supabase docs say shared pooler connections use `postgres.[PROJECT-REF]` and `[ROLE].[PROJECT-REF]` (https://supabase.com/docs/guides/database/connecting-to-postgres), "Port 5432 ... Supavisor for session mode. Port 6543 reaches PgBouncer for the dedicated pooler and Supavisor for shared transaction mode". That matches `external_id = project ref`. The same page distinguishes a paid **dedicated** pooler (PgBouncer, which is bundled in the DB image; see section 11).

**Other facts:** Elixir release, ships its own ERTS; `RLIMIT_NOFILE 100000` in the Dockerfile; Fly.io-oriented env (`FLY_*`), also runs on ECS (the Storage repo's multi-tenant compose runs it as a sidecar). Per-tenant RAM is not documented (not verified).

## 2. Realtime (github.com/supabase/realtime)

**Verdict: native multi-tenant (v2 is "a multi-tenant Phoenix app where every node runs the same code"; `ARCHITECTURE.md`).** [code]

**Tenant resolution:** `lib/realtime/database.ex#get_external_id/1` splits the Host on the first `.` and takes the first label; used in `lib/realtime_web/plugs/assign_tenant.ex` (HTTP) and `lib/realtime_web/channels/user_socket.ex#connect/3` (WebSocket). The compose file spells this out: the container is named `realtime-dev.supabase-realtime` "because realtime constructs tenant id by parsing the subdomain". JWT: `x-api-key` header, falling back to `apikey` param, verified against that tenant's `jwt_secret` / `jwt_jwks` (ARCHITECTURE.md). So a reverse proxy must preserve `Host: <ref>.realtime.example.com` (or rewrite it) for each tenant.

**Tenant store:** the Realtime service's own Postgres, schema `_realtime` (`DB_AFTER_CONNECT_QUERY: SET search_path TO _realtime` in the compose; `volumes/db/realtime.sql` creates the schema). `lib/realtime/api/tenant.ex` fields: `name`, `external_id`, `jwt_secret`, `jwt_jwks`, `postgres_cdc_default`, `max_concurrent_users`, `max_events_per_second`, `max_presence_events_per_second` (1000), `max_payload_size_in_kb` (3000), `max_bytes_per_second`, `max_channels_per_client`, `max_joins_per_second`, `suspend`, `private_only`, `presence_enabled`, `broadcast_adapter` (`gen_rpc` default), `feature_flags`, `migrations_ran`. Plus an `extensions` table holding the `postgres_cdc_rls` settings.
Env defaults used when a tenant is first created: `TENANT_MAX_BYTES_PER_SECOND` (100_000), `TENANT_MAX_CHANNELS_PER_CLIENT` (100), `TENANT_MAX_CONCURRENT_USERS` (200), `TENANT_MAX_EVENTS_PER_SECOND` (100), `TENANT_MAX_JOINS_PER_SECOND` (100). Sensitive columns are encrypted with `DB_ENC_KEY` (legacy AES-128-ECB, 16 chars) or `DB_ENC_KEY_GCM` (AES-256-GCM, 32 chars) (`ENVS.md`).

**How it reaches each tenant's DB:** the `postgres_cdc_rls` extension row carries `settings`: `db_host`, `db_port`, `db_name`, `db_user`, `db_password`, `region`, `poll_interval_ms`, `poll_max_record_bytes`, `ssl_enforced`, plus defaults `publication: "supabase_realtime"`, `slot_name: "supabase_realtime_replication_slot"` (`lib/extensions/postgres_cdc_rls/db_settings.ex`; example in `priv/repo/seeds.exs` and `lib/realtime_web/open_api_schemas.ex`). Per tenant Realtime starts `Realtime.Tenants.Connect` (DBConnection pool; also a `ReplicationConnection` streaming `realtime.messages` inserts off a **logical replication slot** for broadcast-from-DB) and, if Postgres Changes is used, a `PostgresCdcRls` worker with `ReplicationPoller` ("Realtime will be streaming two replication slots", ARCHITECTURE.md). Budget `max_replication_slots`/`max_wal_senders` on each tenant cluster accordingly.

**Management API** (`lib/realtime_web/router.ex`): pipeline `:api` -> `check_auth([:api_jwt_secret, :api_blocklist])` (Bearer HS256 token signed with `API_JWT_SECRET`; `API_JWT_SECRET_NEXT` allows zero-downtime rotation; `API_TOKEN_BLOCKLIST`):
- `resources "/tenants", TenantController, param: "tenant_id"` (index/show/create/update/delete; create is "Create or update tenant")
- `POST /api/tenants/:tenant_id/reload`, `POST /api/tenants/:tenant_id/shutdown`, `GET /api/tenants/:tenant_id/health`, `POST /api/tenants/health` (bulk)
- Swagger at `/swaggerui`, dashboard at `/admin` (`DASHBOARD_USER/PASSWORD`).
The official compose's gateway blocks `/realtime/v1/api/tenants` from public access (`volumes/api/envoy/lds.template.yaml`, route `realtime-v1-api-tenants-blocked`). Note the metrics endpoints use `METRICS_JWT_SECRET`.

**Self-host seeding:** `SEED_SELF_HOST=true` runs `priv/repo/seeds.exs`: inserts one tenant named `SELF_HOST_TENANT_NAME` (default `realtime-dev`), `jwt_secret` = `API_JWT_SECRET`, optional `API_JWT_JWKS`, extension settings from `DB_*`, then runs tenant migrations. This is the "self-host mode" = exactly one tenant, seeded at boot. There is no separate single-tenant code path; self-host is the multi-tenant server with one row.

**Tenant DB coupling:** README compatibility table: role `supabase_admin`; "`DB_USER`: Database user used for all connections (migrations and runtime). **Requires a superuser.**" (ENVS.md). Migrations create the `realtime` schema inside each tenant DB (`lib/realtime/tenants/repo/migrations`, 88 files; `realtime.messages`, `realtime.subscription`, helper functions) and are run per tenant via `Tenants.Migrations.run_migrations/1`. On Postgres 15.14.1.018+, "Migrations need a superuser. Tenant grants don't. supautils manages the policies" (README). PG < 14 unsupported. Also needs `log_min_messages` settable (hence superuser on 14).

**Footprint:** one shared BEAM; 211 MiB idle in the 2024 `docker stats` (supabase discussion #26159, old version, single tenant). Cluster via `CLUSTER_STRATEGIES` (`EPMD`, `DNS`, `POSTGRES`), `gen_rpc` between nodes. `MAX_CONNECTIONS` default 16384 websockets. Per-tenant RAM not documented (not verified).

## 3. Storage API (github.com/supabase/storage)

**Verdict: native multi-tenant.** [code]

**Mode switch:** `src/config.ts`: `isMultitenant = getOptionalConfigFromEnv('MULTI_TENANT', 'IS_MULTITENANT') === 'true'` (new name `MULTI_TENANT`, legacy `IS_MULTITENANT` still accepted). Each env has a legacy alias: `DATABASE_MULTITENANT_URL` / `MULTITENANT_DATABASE_URL`, `DATABASE_MULTITENANT_POOL_URL`, `SERVER_ADMIN_API_KEYS` / `ADMIN_API_KEYS`, `AUTH_ENCRYPTION_KEY` / `ENCRYPTION_KEY`, `REQUEST_X_FORWARDED_HOST_REGEXP` / `X_FORWARDED_HOST_REGEXP`, `SERVER_ADMIN_PORT` / `ADMIN_PORT` (default 5001). Single-tenant mode sets the tenant id from `PROJECT_REF` or `TENANT_ID` (else `storage-single-tenant`); the official compose uses `TENANT_ID: ${STORAGE_TENANT_ID}` with `DATABASE_URL`.

**Tenant resolution:** `src/http/plugins/tenant-id.ts`: in multitenant mode, reads the `x-forwarded-host` header and matches it against the regexp; `request.tenantId = result[1]`. The sample regex in `.env.sample` and `docker-compose-multi-tenant.yml` is `^([a-z]{20}).local.(?:com|dev)$` (a 20-letter project ref subdomain). **The `Host` header is not used; the proxy must set `X-Forwarded-Host`.** Requests from a host that does not match fall through with the default (empty) tenant id and fail with `MissingTenantConfig`. Admin routes take the tenant id from the URL param (`adminTenantId`).

**Tenant store:** the "multitenant DB" (`DATABASE_MULTITENANT_URL`, optional pooler `DATABASE_MULTITENANT_POOL_URL`), migrations in `migrations/multitenant/` (`0001`: `tenants(id text PK, anon_key, database_url, jwt_secret, service_key)`, later: pool options, `jwks`, `file_size_limit`, feature flags, `migrations_version/status`, `tenants_s3_credentials`, `tenants_jwks`, tracing mode, `disable_events`). `database_url`, `jwt_secret`, `anon_key`, `service_key` are encrypted with `encrypt()` using `AUTH_ENCRYPTION_KEY` (`src/internal/auth/crypto.ts`). Config is cached in-process and invalidated by a Postgres notify trigger (`0003-add-notify-trigger.sql`, `onTenantConfigChange`).

**Admin API** (`src/http/routes/admin/tenants.ts`; separate listener on `SERVER_ADMIN_PORT`; every route requires an `apikey` request header in the `SERVER_ADMIN_API_KEYS` comma list, `src/http/plugins/apikey.ts`): `GET /` (list), `GET /:tenantId`, `POST /:tenantId` (create; encrypts and stores, then immediately runs migrations on the tenant DB up to `DB_MIGRATIONS_FREEZE_AT`; on failure registers the tenant with `progressiveMigrations`), `PATCH /:tenantId`, `PUT /:tenantId` (upsert), `DELETE /:tenantId`, plus migration/health helper routes. Body fields: `anonKey`, `serviceKey`, `jwtSecret`, `jwks`, `databaseUrl`, `databasePoolUrl`, `maxConnections`, `fileSizeLimit`, `deleteObjectsLimit`, `tracingMode`, `disableEvents`, `subscriptionTier`, `features{imageTransformation{enabled,maxResolution}, purgeCache, s3Protocol, icebergCatalog{...}, vectorBuckets{...}}`. `ADMIN_RETURN_TENANT_SENSITIVE_DATA=false` omits decrypted secrets from GETs.
Other admin routes: `admin/migrations.ts`, `admin/jwks.ts`, `admin/s3.ts` (per-tenant S3-protocol credentials), `admin/objects.ts`, `admin/queue.ts`, `admin/iceberg-admin.ts`.

**Migration strategy:** `DB_MIGRATIONS_STRATEGY` = `on_request` (default) | `progressive` | `full_fleet` (`MultitenantMigrationStrategy`); `DB_MIGRATIONS_FREEZE_AT` pins how far to migrate tenants (use it to hold the fleet at a schema level during rollouts); `DB_ALLOW_MIGRATION_REFRESH`. 73 tenant migrations in `migrations/tenant/` create the `storage` schema (buckets, objects, S3 multipart tables, etc.) **in each tenant's database**, state in `storage.migrations`.

**Tenant DB coupling:** `DB_INSTALL_ROLES` (default in compose true) lets migrations create `anon`/`authenticated`/`service_role` (`DB_ANON_ROLE`, `DB_SERVICE_ROLE`, `DB_AUTHENTICATED_ROLE`); `DB_SUPER_USER` (default `postgres`) is used for migration-time operations. In the official compose the runtime role is `supabase_storage_admin` (created by the supabase/postgres init scripts, `00000000000002-storage-schema.sql`). Storage also uses `pg-boss` (schema `pgboss`) for its queue when `PG_QUEUE_ENABLE=true`; the queue DB is configurable (`pgQueueConnectionURL`) so it can be shared rather than per tenant.

**Object isolation:** `src/storage/locator.ts#TenantLocation.getKeyLocation` builds `${tenantId}/${bucketId}/${objectName}`, so all tenants can share ONE S3 bucket (`STORAGE_S3_BUCKET`) and are separated by key prefix. Per-tenant bucket-level IAM isolation is not available in this layout [infer: you would need a prefix-scoped IAM policy, which Storage itself does not mint].

**S3 protocol / imgproxy:** S3-compatible endpoint is per-tenant (`feature_s3_protocol`, credentials in `tenants_s3_credentials`; `S3_PROTOCOL_ACCESS_KEY_ID/SECRET` in single-tenant compose). Image transformation: `IMGPROXY_URL` env (+ `ENABLE_IMAGE_TRANSFORMATION`/`IMAGE_TRANSFORMATION_ENABLED`) and per-tenant `feature_image_transformation` / `image_transformation_max_resolution`. imgproxy itself is stateless (see section 12).

**Footprint:** Node.js/Fastify; 39.5 MiB idle in the 2024 stats. Multi-tenant compose in the repo (`docker-compose-multi-tenant.yml`) wires: storage + `tenant_db` + `multitenant_db` + **supavisor** + rustfs (S3) + imgproxy, i.e. Supabase themselves dev-test the "Storage + Supavisor + metadata DB + tenant DBs" topology.

## 4. Auth / GoTrue (github.com/supabase/auth)

**Verdict: single-tenant. Confirmed: multi-instance mode was disabled in 2021 and is documented as unsupported.** [code]

- `README.md` "Inherited features" (lines ~137-146): "Certain inherited features from the Netlify codebase are not supported by Supabase and they may be removed without prior notice... 1. Multi-tenancy via the `instances` table i.e. `GOTRUE_MULTI_INSTANCE_MODE` configuration parameter." Same list: system user, `is_super_admin`, group JWT claims.
- Git history: commit `7862e344` "chore: disabling multi-instance mode" (2021-06-29, supabase/gotrue). The original feature came from netlify PR #40 "multi-instance" (2017).
- Code search of the current tree finds no `MULTI_INSTANCE` symbol. Only leftovers: the nullable `instance_id uuid` column on `auth.users` and the `auth.instances` table (`migrations/00_init_auth_schema.up.sql`, indexes like `users_instance_id_email_idx`), and `auth.instances` still appears in supautils `policy_grants` (postgres repo). Do not treat the column as a tenancy mechanism.

Runtime tenant creation = write a config dir for a new process.

**Per-tenant settings (all env):** `API_EXTERNAL_URL`, `GOTRUE_SITE_URL`, `GOTRUE_URI_ALLOW_LIST`, `GOTRUE_JWT_SECRET` / `GOTRUE_JWT_KEYS` (asymmetric signing keys), `GOTRUE_JWT_ISSUER`, `GOTRUE_JWT_EXP`, `GOTRUE_JWT_AUD`, `GOTRUE_DB_DATABASE_URL` (note: `DATABASE_URL` in the struct tag, `GOTRUE_DB_DATABASE_URL` in compose), `GOTRUE_DB_NAMESPACE` (default `auth`), SMTP, external OAuth providers, SMS, rate limits, MFA, hooks.

**DB coupling:** `GOTRUE_DB_NAMESPACE` default `auth`; migrations run from `./migrations` (template-expanded with the namespace) and need a role that can create the schema/objects: the repo's `init_postgres.sh` creates `supabase_auth_admin NOINHERIT CREATEROLE LOGIN NOREPLICATION`, `CREATE SCHEMA auth AUTHORIZATION supabase_auth_admin`, and `ALTER USER ... SET search_path = auth`. In the supabase/postgres image that role is created by `migrations/db/init-scripts/00000000000001-auth-schema.sql`. No superuser needed after setup. Because `DB_NAMESPACE` is configurable, one DB could in theory hold several auth schemas, but nothing else in the stack (RLS helpers `auth.uid()`, Realtime, Storage policies, supautils) assumes anything other than `auth` [infer: not viable].

**Footprint:** one static Go binary (Dockerfile builds a Go binary); 8.9 MiB resident idle in 2024 `docker stats` (discussion #26159); `MemoryMax=50%` on the hosted VM unit file. Startup: Go binary, DB connection + migration check; fast (not measured). Cheap enough that "one Auth per project" is a reasonable minimal unit.

## 6. postgres-meta (github.com/supabase/postgres-meta)

**Verdict: stateless and effectively multi-DB per request.** [code]

- `README.md` FAQ: "The server is multi-tenant, so it can support multiple Postgres databases from a single server." Also: "What security does this use? None. Please don't use this as a standalone server."
- `src/server/routes/index.ts` `onRequest` hook: reads `x-connection-encrypted`; if present `request.headers.pg = CryptoJS.AES.decrypt(header, CRYPTO_KEY).toString(Utf8)`, else falls back to `PG_CONNECTION` built from `PG_META_DB_URL` or `PG_META_DB_HOST/PORT/NAME/USER/PASSWORD` (+ `PG_META_DB_SSL_MODE`, `PG_META_DB_SSL_ROOT_CERT`). The decrypted value must parse as a URL. Routes then call `createConnectionConfig(request, ...)` and `new PostgresMeta(config)`; `src/lib/db.ts` creates a new `pg.Pool` for the call and ends it (no persistent per-tenant pool). `CRYPTO_KEY` env (or `CRYPTO_KEY_FILE`) must match the caller's key; default `SAMPLE_KEY` (change it). Optional `x-pg-application-name` header, `PG_CONN_TIMEOUT_SECS` (15), `PG_QUERY_TIMEOUT_SECS` (55), `PG_META_MAX_RESULT_SIZE_MB`.
- Studio side (`apps/studio/lib/api/self-hosted/query.ts`, `util.ts`): `encryptString(connectionString)` with `crypto-js` AES using `ENCRYPTION_KEY = process.env.PG_META_CRYPTO_KEY || 'SAMPLE_KEY'`, then `fetch(PG_META_URL + '/query', {headers: {'x-connection-encrypted': ...}})`. In the compose, Studio gets `PG_META_CRYPTO_KEY` and meta gets `CRYPTO_KEY: ${PG_META_CRYPTO_KEY}`. This header is **how hosted Studio reaches many projects too** (hosted uses `PLATFORM_PG_META_URL`; hosted-side code is not public, so "hosted does it the same way" is [infer], but the multi-tenant capability is in the repo).
- Footprint: Node, ~59 MiB (2024). One shared instance is enough for the whole fleet. It holds no state, but whoever holds `CRYPTO_KEY` (or can reach the port) can run SQL as any DB it can connect to, so it must stay on a private network behind the control plane. Compose gateway exposes it at `/pg/` behind apikey (`pg-protected` route) - do not do that in a multi-tenant fleet.

## 8. Edge Runtime (github.com/supabase/edge-runtime)

**Verdict: one process can host many tenants' functions as isolates, but tenant routing/auth is user-code (the "main service"), not built in.** [code]

- `README.md` Architecture: **main runtime** = entry point that proxies to user runtimes, "Has no user-facing limits", "Has access to all environment variables"; **user runtime** = executes user code, "Limits are required to be set such as: Memory and Timeouts", "Has access to environment variables explicitly allowed by the main runtime". Rust server embedding Deno/V8; WASM supported; "Beta Software".
- CLI flags (`cli/src/flags.rs`): `--main-service <DIR>` (default `examples/main`), `--event-worker`, `--policy per_worker|per_request|oneshot` (default `per_worker`), `--max-parallelism <COUNT>` (max workers in the pool), `--request-wait-timeout` (10000 ms), `--main-worker-request-idle-timeout`, `--graceful-exit-timeout` (15 s), `--static`, TLS cert flags. The compose runs `start --user-worker-request-idle-timeout 150000 --main-service /home/deno/functions/main`.
- Self-host main service (`supabase/docker/volumes/functions/main/index.ts`): verifies JWT (HS256 secret and/or JWKS via `jose`, `VERIFY_JWT`), takes the function slug from the URL path, `servicePath = /home/deno/functions/<slug>`, then `EdgeRuntime.userWorkers.create({servicePath, memoryLimitMb: 150, workerTimeoutMs: 400_000, context:{supervisor:{requestAbsentTimeoutMs}}, noModuleCache, importMapPath, envVars})` with `envVars = {...Deno.env.toObject(), SUPABASE_FUNCTION_SLUG}` and retry on `WorkerAlreadyRetired`. Error taxonomy: boot error 503, resource limit 546, idle timeout 504.
- Env injected: `SUPABASE_URL`, `SUPABASE_PUBLIC_URL`, `SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY`, `SUPABASE_PUBLISHABLE_KEYS` / `SUPABASE_SECRET_KEYS` (JSON maps keyed by name; `"default"` in the compose), `SUPABASE_DB_URL`, `JWT_SECRET`, `SUPABASE_JWKS`, `VERIFY_JWT`. Note the sample passes the **entire** main env (including `SUPABASE_DB_URL`) to every worker; a multi-tenant main service must instead construct per-tenant `envVars` (secrets and per-tenant `SUPABASE_URL`), which the API supports.
- Isolation model: V8 isolate per worker with memory/timeout limits, not a VM/container per tenant. For hostile multi-tenant code, V8-level isolation is the weakest link in the stack [infer]. How hosted Supabase wires its (closed) main service and subhosting (`deno-subhosting-events` is one of Logflare's seeded sources) is not public (not verified).
- Footprint: ~21 MiB idle for the supervisor process (2024); per-worker up to `memoryLimitMb`.
- No DB coupling (functions use `SUPABASE_DB_URL`/supabase-js over the gateway). Studio's function UI reads/writes the `edge-functions` folder (`EDGE_FUNCTIONS_MANAGEMENT_FOLDER`).

## 10. Kong -> Envoy (API gateway)

- **Self-host default changed in Aug 2026:** discussion https://github.com/orgs/supabase/discussions/48048 ("Envoy becomes the default API gateway (breaking change)", posted 2026-07-17): Kong OSS "effectively stopped advancing", Kong removed free mode in 3.10; Envoy gives "config-as-code", translation of `sb_publishable_*`/`sb_secret_*` opaque keys into internal JWTs, hardened defaults; gateway service is now `api-gw` (container `supabase-envoy`, aliases `envoy` and `kong`), HTTP only on 8000, TLS via `docker-compose.caddy.yml`/`nginx.yml`; Kong is opt-in via `docker-compose.kong.yml` (`kong/kong:3.9.3`, DB-less declarative config `volumes/api/kong.yml`).

API-key (`apikey`) checking appears to live elsewhere (edge) in hosted; this tree has no `key-auth` consumer config for hosted [not verified].
- For a multi-tenant fleet, a shared edge router (host or path -> tenant -> upstream set, plus per-tenant apikey/JWT validation) has to be built; Envoy supports dynamic xDS (hosted uses file-based `cds.yaml`/`lds.yaml`), so a control plane can push per-tenant listeners/clusters.

| Tuned, `database-optimizations.service`, `gotrue-optimizations.service`, `postgrest-optimizations.service`, `services.slice` | | Per-VM resource tuning (`MemoryMax=50%` for gotrue) |

**Roles created by the init scripts** (`migrations/db/init-scripts/*`, `migrations/db/migrations/*`): `supabase_admin` (superuser, owner), `postgres` (demoted: `10000000000000_demote-postgres.sql`; created as `create role postgres superuser` then demoted/privileged via supautils), `anon`, `authenticated`, `service_role` (BYPASSRLS), `authenticator` (noinherit), `supabase_auth_admin`, `supabase_storage_admin`, `supabase_functions_admin` (post-setup), `supabase_replication_admin`, `supabase_etl_admin`, `supabase_read_only_user` (BYPASSRLS), `dashboard_user`, `pgbouncer`, plus the privileged-role membership scheme. Passwords are set in the compose via `volumes/db/roles.sql`. Schemas: `auth`, `storage`, `realtime`, `extensions`, `graphql`, `graphql_public`, `vault`, `pgsodium`, `net`, `cron`, `pgbouncer`, `_realtime`/`_supavisor`/`_analytics` (internal, in `_supabase` DB).

**What this means for tenancy at the DB layer:**
- The unit is a Postgres **cluster** (hosted: one VM per project). Roles are cluster-global names (`anon`, `authenticated`, `service_role`, `authenticator`, `supabase_*`): two projects in one cluster (database-per-project) would share role names and, importantly, their passwords/attributes; `authenticator`/`supabase_auth_admin` passwords and the `pgsodium` root key are cluster-wide. That is why "one database per project in one cluster" (Sbarbase-style) needs per-project role prefixing or stays weaker isolation [infer; not tested].
- `pg_cron` and `pg_net` are bound to a single DB per cluster.
- Realtime needs superuser on the tenant DB and 1-2 logical slots per active tenant; Storage and Auth only need their own roles; PostgREST needs `authenticator`.
- Docker image variants: `supabase/postgres:17.6.1.136` in the official compose (2026-06-17; previously 15.8.1.085); `Dockerfile-orioledb-17`; `Dockerfile-multigres` (Multigres: README of Realtime says "Only Postgres >= 17.x and every commit waits for a standby"); `Dockerfile-kubernetes` and `docker/pgctld` (a process manager, `pgctld-wrapper.sh`, templates for postgresql.conf) for k8s-style operation.

## 12. Vector and imgproxy

- **Vector** (`timberio/vector:0.53.0-alpine` in compose; `vector.service.j2` on the hosted VM): stateless log agent; the official config reads the Docker socket (`volumes/logs/vector.yml`), tags events (`project`, `tenantId`), and POSTs to Logflare `http://analytics:4000/api/logs?source_name=...` with `x-api-key: ${LOGFLARE_PUBLIC_ACCESS_TOKEN}`. ~40 MiB. Per-host sidecar; the only per-tenant knob is the `project` stamp.
- **imgproxy** (`darthsim/imgproxy:v3.31.4`): stateless Go image transformer, ~18 MiB, called by Storage via `IMGPROXY_URL`; compose config uses `IMGPROXY_LOCAL_FILESYSTEM_ROOT` or (multi-tenant compose) an S3 setup. One shared instance for all tenants.

## What this means (analysis, my inference unless labeled otherwise)

### Sort by "shareable" vs "per tenant"

**Can be ONE shared deployment across all tenants (native multi-tenant, runtime-managed API, tenant row in a metadata DB):**
1. **Supavisor** - tenant = project ref; `PUT /api/tenants/<ref>` with `db_host/db_port/db_database`, `auth_query = SELECT * FROM pgbouncer.get_auth($1)`, a manager user (`pgbouncer`) and password. Clients connect as `postgres.<ref>@pooler.example.com:6543`. Keep it as the **only** public DB entrypoint; per-tenant limits (`default_pool_size`, `default_max_clients`, `allow_list`) and metrics come for free.
2. **Realtime** - tenant = subdomain of the Host header; `POST /api/tenants` with the tenant's `jwt_secret` (or JWKS) and `postgres_cdc_rls` settings pointing at that tenant's DB. Route `<ref>.realtime.<domain>` (or rewrite Host to that) to the shared fleet. Cost: superuser DB credentials per tenant held by the shared service (stored AES-encrypted), 1-2 replication slots per active tenant.
3. **Storage API** - tenant = capture group of `X-Forwarded-Host`; `POST /tenants/<ref>` on the admin port with `databaseUrl` (+ `databasePoolUrl` = the Supavisor URL), `jwtSecret`, `anonKey`, `serviceKey`, features. One shared S3 bucket with automatic `<ref>/<bucket>/<key>` prefixing. Shared imgproxy.
4. **postgres-meta** - one stateless instance, per-request encrypted connection string (internal network only).
5. **Studio** - one instance, but needs the project-aware API-layer fork (Studio is the only shared component whose multi-project support is not native). Fork scope is narrow: swap `getConnectionString()`, `DEFAULT_PROJECT`, `getProjectSettings()` and the `projects`/`organizations` stubs for a lookup against a control-plane DB keyed by `[ref]`; point `x-connection-encrypted` at each project's DB.
6. **Logflare + Vector** - shared, with the existing `project` field/`@project` query parameter convention (heaviest RAM; make it optional/off in a minimal tier).
7. **imgproxy** - trivially shared.
8. **Edge Runtime** - shareable *only* if you write the multi-tenant main service (tenant -> servicePath + per-tenant `envVars`, memory/timeouts per worker). V8-isolate isolation is weaker than process/VM isolation, so treat it as a tier choice, not a default.
9. **Edge/gateway** - shared L7 router is something you must build (host -> tenant -> upstreams, per-tenant apikey/JWT validation); Envoy with xDS is the natural base. Not native.

**Must be per tenant (single-tenant by design, no tenant column/header):**
1. **Postgres** (the database/cluster; roles, `pgsodium` root key, `pg_cron`/`pg_net` single-DB binding make "database per project in a shared cluster" a weaker, role-name-clashing option).
2. **Auth/GoTrue** - one process per tenant (multi-instance removed in 2021; ~9 MiB RSS, one static Go binary; config via env or `--config-dir` + SIGUSR1 reload; DB role `supabase_auth_admin`).
3. **PostgREST** - one process per tenant (single `db-uri`, `jwt-secret`, `db-schemas`; static binary; tens of MB). No upstream multi-DB support; the issue to route by Host is open since 2023 and the multi-tenant proposal was closed.

### Minimal per-tenant unit

The smallest unit that matches how Supabase hosted is built is:

```
per-tenant:  Postgres (supabase/postgres) + GoTrue + PostgREST     <- hosted bundles these on one VM (ansible playbook)
shared:      Supavisor, Realtime, Storage (+ imgproxy, S3 bucket), postgres-meta, Studio(forked), Logflare/Vector (optional), edge router
```

That is exactly the split Supabase's own repos encode: `supabase/postgres/ansible` bundles Postgres, PgBouncer, GoTrue, PostgREST, Envoy and admin tooling on a project VM, while Supavisor, Realtime and Storage are the three services that ship tenant tables, tenant-admin APIs and tenant-resolving request handling [code]; and Storage's `docker-compose-multi-tenant.yml` runs Storage + Supavisor + metadata DB + tenant DB, i.e. a multi-tenant dev topology. That the hosted platform actually runs Realtime/Storage/Supavisor as shared fleets is [infer]: the code strongly implies it, the topology is not documented in the public repos (Supabase's architecture page only shows the logical per-project component diagram; the Supavisor docs say "shared pooler").

A tenant's three per-tenant processes (Postgres, GoTrue, PostgREST) fit one small VM or one pod with 3 containers (GoTrue + PostgREST add roughly 25-150 MiB combined on top of Postgres based on the 2024 stats, vs several hundred MB for Postgres itself). So "native-as-possible" realistically means: do not multiplex the DB, Auth, or REST; do multiplex everything with a tenant table.

### Control-plane shape this implies

Creating a tenant = (1) provision DB (cluster/VM/pod) with the supabase/postgres image and set role passwords; (2) start GoTrue + PostgREST with the tenant's JWT secret/keys (same secret is used by Realtime and Storage tenant rows and the gateway); (3) call the three admin APIs: Supavisor `PUT /api/tenants/<ref>`, Realtime `POST /api/tenants`, Storage `POST /tenants/<ref>` (Storage runs the tenant migrations itself; Realtime runs its migrations on first connect/seed); (4) register routes in the shared edge router; (5) write the project row Studio reads. Secrets that must be coordinated across components per tenant: DB password(s), JWT secret (HS256) or JWKS, anon/service keys; plus fleet-level keys: `VAULT_ENC_KEY` (Supavisor), `DB_ENC_KEY(_GCM)` (Realtime), `AUTH_ENCRYPTION_KEY` (Storage), `CRYPTO_KEY`/`PG_META_CRYPTO_KEY` (meta+Studio), `API_JWT_SECRET` (Supavisor and Realtime admin), `SERVER_ADMIN_API_KEYS` (Storage).

### Risks and sharp edges found

- **Shared secrets in shared services:** Realtime and Storage store each tenant's superuser/service DB URL and JWT secret (encrypted at rest with a single fleet key). A compromise of the shared fleet exposes every tenant. Plan KMS/rotation (Realtime supports `API_JWT_SECRET_NEXT` and AES-GCM backfill; Supavisor/Storage rotation not verified).
- **Realtime superuser requirement** on every tenant DB (README/ENVS.md). Realtime also needs logical replication slots and a replication-capable path: connect directly to the DB, not through a transaction pooler.
- **Header contracts differ:** Realtime = `Host` first label; Storage = `X-Forwarded-Host` regex capture group; Supavisor = username suffix / SNI. The edge router must set both consistently and strip client-supplied `X-Forwarded-Host`.
- **Admin APIs must never be exposed publicly:** Realtime `/api/tenants` (the official Envoy config blocks it), Storage admin port 5001, Supavisor `/api/*` and `/metrics`, postgres-meta (root-level SQL by header).
- **Kong -> Envoy transition (Aug 2026)** changes the reference gateway; any plan built on `kong.yml` consumers is on a deprecated default path, but a multi-tenant edge must be custom regardless.
- **PostgREST upstream is hostile to multi-tenancy** (closed proposals), so don't plan on it changing.
