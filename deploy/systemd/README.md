# deploy/systemd

systemd units for Supavise, embedded in the binary (`embed.go`) and installed by `supavise system converge` (needs root; `install-units` is its alias) or by the installer.

| File | What |
|---|---|
| `supavise-postgres@.service`, `supavise-gotrue@.service`, `supavise-postgrest@.service` | per-project templates; the instance is the ref |
| `supavise-supavisor`, `supavise-realtime`, `supavise-storage`, `supavise-pgmeta`, `supavise-studio` | fleet singletons |
| `supavise-imgproxy`, `supavise-edge-runtime` | optional singletons |
| `supavise-edge-bundle@<ref>` | one-shot, started by the API for each upload of Edge Function sources. Runs `edge-runtime bundle` under its own uid (`DynamicUser=yes`, the one exception to `User=supavise`) with a module cache per project (`/var/cache/supavise-edge-bundle/<ref>`, removed by `supavise projects delete`), in a sandbox that sees only the upload's sources (read-only), one output directory and the artifacts (see "The exception" and `internal/functions/README.md`) |
| `supavise-diskquota@.service` | root one-shot, started by the daemon over D-Bus when a project's disk size is set on an XFS data volume mounted with `prjquota` (`internal/diskquota`): `supavise system set-disk-quota <ref>` takes the ref from the unit name (checked), reads a project id and a size in GB from `projects/<ref>/disk-quota` (range-checked), refuses a project directory that is a link, and runs `xfs_quota`. `PrivateDevices` is off (`xfs_quota` needs the block device node); capabilities are `CAP_SYS_ADMIN`, `CAP_FOWNER`, `CAP_DAC_OVERRIDE`, `CAP_DAC_READ_SEARCH` and `CAP_SYS_RESOURCE`; no network; writes only under `/var/lib/supavise` |
| `supavise.slice`, `supavise.service` | the slice every unit runs in (`systemctl status supavise.slice` shows the total); the daemon (`supavise serve`: Management API, edge proxy, lifecycle engine; starts active projects at boot) |
| `50-supavise.rules` | polkit rule: the `supavise` user may start, stop and tune `supavise-*` units and `supavise.service`, except `supavise-upgrade.*`, the root unit that may be mid-upgrade (manage-units only; enabling units and daemon-reload need root, through `converge`) |
| `supavise-upgrade.service` and `.timer` | the opt-in unattended upgrade and the OS reboot, inside the maintenance window (`supavise update run`, as root; the daemon, not this unit, checks for releases). Its state lives in `/var/lib/supavise-upgrade`, outside the state directory every other unit can write; the command takes that path from `$STATE_DIRECTORY`, never from `config.toml`. `converge` writes the timer from `[update]` in `config.toml` (the file here is the rendering with the defaults, kept in step by `internal/update`'s tests); see `deploy/README.md`, Update |
| `supavise-basebackup@.service` and `.timer`, `supavise-basebackup-prune.service` and `.timer` | nightly base backup per project and the node-wide retention prune. The daemon and the lifecycle engine start the timer instances over D-Bus; `converge` writes `supavise-basebackup@.timer` with `backup.base_backup_on_calendar` |

`supavise system converge` also writes, for every `supavise*.service` unit above, a drop-in that makes the unit wait for the volume its state lives on: `<unit>.d/10-supavise-data-mount.conf` (`RequiresMountsFor=/var/lib/supavise`) when the state directory is a mount point, and `<unit>.d/20-supavise-etc-mount.conf` (`RequiresMountsFor=/etc/supavise`) when the config directory is one, as on AWS where `/etc/supavise` is a bind mount of the data volume. A volume that is missing at boot then stops the units from starting against an empty directory on the root disk. `supavise-upgrade.service`, whose state is on the root disk, gets only the second. The drop-ins are not unit templates: `internal/hostsetup` writes them, and the unit files here do not change. Nothing here changes what a unit that already runs does, and converge restarts none; only a daemon-reload follows.

`supavise.service` binds the mesh port (`[node] peer_listen`, 7443; above 1024, so no capability change). A change to its hardening that the mesh needs (address families, `IPAddressAllow` for peers) ships through `converge` like any other unit change: the daemon restart that `supavise upgrade` does anyway applies it. Converge also opens that port in ufw when ufw is active; on AWS the security group does it.

Every service unit but `supavise-edge-bundle` runs as `User=supavise`, reads `/var/lib/supavise/projects/<ref>/<svc>.env` (0600, by systemd, before the unit's mount namespace exists) and executes `<svc>.run`; `units.Supervisor.Render` writes both, so the templates never change per project. `MemoryMax` and `CPUQuota` are per-unit drop-ins applied over D-Bus. Logs go to journald, selected by unit name (`SyslogIdentifier` equals the unit).

Hardening: `NoNewPrivileges`, `ProtectSystem=strict` with a `ReadWritePaths` of the unit's own state directory only (the allowlist below), `ProtectHome`, `PrivateTmp`, `PrivateDevices` (`/dev/shm` stays available), kernel protections, empty capability set, `RestrictAddressFamilies`, `UMask=0027`. `MemoryDenyWriteExecute` is off for the artifacts (Postgres JIT, the BEAM and Node map writable and executable memory); `supavise.service` sets it. Postgres stops on SIGINT (fast shutdown) with `KillMode=mixed` and 90 s. The unit paths assume the default `state_dir` of `/var/lib/supavise`; `internal/units` tests check that the templates and the Go layout agree. The `systemd-smoke` job of `linux.yml` (Ubuntu 24.04, amd64 and arm64) starts the units; if a hardening option breaks an artifact there, relax it in the affected template and record why in the template.

## Trust model: what the sandbox does and does not do

Every unit, Postgres included, runs as `supavise`, and so does the daemon. The mount namespace of each unit and a few other controls do the isolating. This section says what they cover and what they do not, because a node hosts projects that run user code (SQL functions, extensions such as pg_net and http, an agent with `execute_sql`, a compromised app).

### What is isolated

| Threat | Control |
|---|---|
| Code of one project reads another project's data directory, environment files, launcher or backups by path | Allowlist mount namespace (below): every unit sees an empty tmpfs where `/var/lib/supavise` is, plus its own paths |
| Code in a unit talks to systemd (the polkit rule lets the `supavise` user tune `supavise-*` units) | `InaccessiblePaths=-/run/dbus` hides the system bus from every `supavise-*` unit; only the daemon uses it |
| Code in a unit reads the master key or `config.toml` (S3 and DNS credentials) | `InaccessiblePaths=-/etc/supavise` on every unit |
| Code in a project's Postgres reads or overwrites another project's WAL or base backups, or its own | The Postgres unit has no backup directory and no backend credentials. `archive_command` and `restore_command` are `supavise wal push\|fetch --socket <projects/<ref>/wal/r.sock>`: the daemon (the only holder of the credentials) does the storage I/O over a unix socket that only that project's unit can see. The socket serves one project: it refuses a push for another ref, and a fetch of another ref's archive unless the daemon recorded it as the source of this project's restore |
| Code reaches the cloud instance credentials (EC2 role: the whole backup bucket, Route 53) | `IPAddressDeny=169.254.169.254 fd00:ec2::254` on every `supavise-*` unit: Postgres, GoTrue, PostgREST, postgres-meta, Realtime, Supavisor, Storage, Studio, imgproxy, the edge runtime. Only `supavise.service` and the `supavise-basebackup` units keep access |
| A stopped daemon makes WAL pile up somewhere insecure | There is no other path: with the daemon down `archive_command` fails and Postgres retries it (the segment stays in `pg_wal`); `restore_command` exits 126, which aborts recovery |

`tests/linux/systemd-smoke.sh` and `fleet-smoke.sh` check these from inside the namespaces of real units; `internal/backup` tests (`relay_test.go`, `cli_test.go`) pin the relay contract and exit statuses.

**The exception.** `supavise-edge-bundle@<ref>.service` runs another person's source code through a bundler that opens whatever paths the code names, so a mount namespace is not enough: under the `supavise` uid an upload could import `/proc/<pid>/root/...` of any other unit and carry its files (every project's `functions-env.json` included) out in its bundle. It therefore runs under a dynamic uid, with `ProtectProc=invisible` and `ProcSubset=pid` (they hide only other users' processes, so they work for it and not for the `supavise` units). Its module cache is per project, because with one cache for the node an upload of project B could import what an upload of project A had made the bundler download (a private npm package fetched with A's `.npmrc`); the root one-shot `supavise-edge-bundle-clean@<ref>.service` deletes a project's cache (a lowercase ref only; it removes `/var/cache/private/supavise-edge-bundle/<ref>`, nothing else). `tests/linux/functions-smoke.sh` probes both. **The Edge Runtime does not need the same treatment against its user workers**: they are isolates inside its process, with no path to name under `/proc` (`internal/functions/mainservice/README.md`, "Isolation, as measured"). A compromise of the runtime itself (a V8 escape) is the case the one-uid-per-project hardening below addresses.

**What the allowlist buys.** A service cannot read, by plain path, the master key and config (`/etc/supavise`), TLS keys, other projects' data and backups, or sibling units' environment files. That stops accidents, a service that wanders through the file system, and exploit classes that reach only paths and not `/proc`. It is defense in depth, not a boundary: **treat every project on a node as sharing a trust domain with every other project and with the control plane.** `POSTGRES_PASSWORD` (the `supabase_admin` superuser password, read only on the first boot) is rendered into `postgres.env` only until the cluster is initialized, then removed and the cluster restarted; the other passwords cannot be removed from the environments of the units that need them.

### What is not isolated

**The mount sandbox is not a boundary against code that runs inside a unit.** All services share one uid, and the kernel lets a process of a uid open `/proc/<pid>/environ` and `/proc/<pid>/root` of every other process of that uid. A compromised GoTrue or PostgREST of project A can therefore read `/proc/<postgres-pid-of-B>/root/...` (B's data directory) and the environment of every other unit, where B's JWT secret and database passwords sit; a file-read bug in a service reaches the same files. `TemporaryFileSystem`, `BindPaths` and `InaccessiblePaths` do not stop that, and no unit option available on Ubuntu 22.04, 24.04 and Debian 12 (systemd 249 to 255) does: `ProtectProc=invisible` hides only other users' processes, and `PrivatePIDs=` needs systemd 257.

**What still holds, by kernel rule.**

- *The daemon and backup units.* `ptrace_may_access` (which guards `/proc/<pid>/environ` and `/proc/<pid>/root`) refuses a same-uid caller when the target holds a permitted capability the caller lacks. Every `supavise-*` unit that runs tenant code has an empty capability set; `supavise.service`, `supavise-basebackup@.service` and `supavise-basebackup-prune.service` hold `CAP_NET_BIND_SERVICE` (`CapabilityBoundingSet=` and `AmbientCapabilities=`), so a tenant unit cannot read their environment, their `/proc/<pid>/root` (`/etc/supavise/master.key`, `config.toml`) or their memory. The daemon needs the capability for ports 80 and 443; the backup units carry it only for this check. Do not remove it from these units, and do not give it to a unit that runs tenant code. `systemd-smoke.sh` reads the capability sets.
- *The CLI.* A command an operator runs (`sudo -u supavise supavise ...`) runs in the host mount namespace, so its `/proc/<pid>/root` shows `/etc/supavise/master.key`, `config.toml` and the backups directory, and it holds no capability. Every `supavise` process therefore calls `prctl(PR_SET_DUMPABLE, 0)` first thing in `main` (`cmd/supavise/harden_linux.go`): a non-dumpable process refuses `PTRACE_MODE_READ` to a same-uid caller without `CAP_SYS_PTRACE`, which covers `/proc/<pid>/root`, `environ` and `mem` for the whole run; `exec` resets the flag, so children (`psql`, `pg_basebackup`) are unaffected. What stays readable from another unit is the tenant-facing processes: every project's Postgres, GoTrue and PostgREST, and the fleet services.
- *The WAL relay.* A process of any unit can open another project's socket through `/proc/<pid-of-that-postmaster>/root/...`, so the relay does not rely on the mount namespace alone. On every connection it reads the peer's pid (`SO_PEERCRED`) and cgroup, and serves only a peer in `supavise-postgres@<ref>.service` for the socket of `<ref>`, in a `supavise-basebackup` unit, or outside every `supavise-*` unit (the daemon, an operator's shell). Any other `supavise-*` unit gets a closed connection, and so does a peer whose cgroup cannot be read. The pid could be reused between the connection and the read: on Linux 6.5 and later the check takes a pidfd (`SO_PEERPIDFD`) and refuses when the process is gone after the read; older kernels (Debian 12 has 6.1) compare the process's start time before and after the read, which closes only the window of the read itself, so exploiting what remains needs code execution in a unit plus a pid race. The check is `internal/backup/relay_peer.go`; `systemd-smoke.sh` moves a `curl` into other units' cgroups and expects it to be refused.

The controls above close the paths that do not go through `/proc`: plain file reads, the metadata service, the backup credentials and the other projects' archives. They do not make a node safe against an attacker with code execution as the `supavise` user inside one unit. Postgres runs C extensions and is reachable through Supavisor, so it is the most exposed process; a tenant who can run `COPY ... TO PROGRAM` (a superuser: Supabase does not give that role to the `postgres` user) or load an untrusted extension has code execution inside the unit and reaches the others through `/proc`. Practical consequences:

- Other projects' credentials and data are out of reach of SQL, `pg_net`/`http`, an `execute_sql` agent and a plain file read, and within reach of an exploit that gives code execution as `supavise`.
- Another project's database is also reachable over loopback TCP, behind scram-sha-256; the passwords are not in any file a unit can open.
- The Edge Runtime runs user code of every project in one process tree. Keep `IPAddressDeny` on it, and materialize each project's functions under a directory the runtime owns (for example `system/edge-runtime/functions/<ref>/`), never by binding `/var/lib/supavise/projects` (every project's environment files and data directories): `TestTemplatesContainment` fails a template that binds more than the allowlist.

### Allowlist, per template

`TemporaryFileSystem=/var/lib/supavise:ro` replaces the state directory with an empty tmpfs, and the unit gets back only:

| Unit | Read-only | Writable |
|---|---|---|
| `supavise-postgres@<ref>` | `artifacts/`, `projects/<ref>/postgres.run`, `projects/<ref>/wal/` (the relay socket; connecting needs no write access) | `projects/<ref>/postgres/`, `artifacts/postgres/` (the launcher chmods a script there on first boot) |
| `supavise-gotrue@<ref>`, `supavise-postgrest@<ref>` | `artifacts/`, `projects/<ref>/<svc>.run` | `projects/<ref>/<svc>/` |
| fleet singletons | `artifacts/`, `projects/system/<svc>.run` | `system/<svc>/` (optional: create it first); Studio also `artifacts/studio/` |
| `supavise-basebackup@<ref>` | `projects/system/postgres/sock` (the registry), `projects/<ref>/postgres/` (the data directory it archives), `system/storage/objects/stub/<ref>/` (the project's Storage objects, which it copies to the backend; absent for a project without objects) | `projects/<ref>/wal/` (a CLI relay's socket while the daemon is down), `backups/` (the file backend; absent on S3) |
| `supavise-basebackup-prune` | `projects/system/postgres/sock` | `backups/` |

No template binds a project or system directory as a whole, none needs to read an environment file (systemd, PID 1, reads `EnvironmentFile=` before it builds the namespace), and none sees `/etc/supavise`, the `backups` directory or the certificates. `internal/units` (`TestTemplatesContainment`) pins this shape; `systemd-smoke.sh` and `fleet-smoke.sh` check it on a real node.

- The Postgres template also hides systemd-resolved's `/run/systemd/resolve/io.systemd.Resolve` and nscd's socket (besides the D-Bus system bus, which every template hides): they are ways out of the IP filter of a branch with denied egress, which `IPAddressDeny` does not cover. systemd 255 cannot change `InaccessiblePaths` of a running unit over D-Bus, so every Postgres unit hides them.
- The WAL relay directory `projects/<ref>/wal/` is created by the lifecycle engine before the cluster starts (`PostgresPlane.prepare`), and the daemon's `backup.Relay` serves one socket in it per project, picking up new projects within three seconds or at once through the engine's hook. The bind is optional (`-` prefix), so a unit that predates the directory still starts but archives nothing until the directory exists and the unit restarts: a node upgraded from before the relay needs one restart of each project's Postgres (the daemon's next start of a project does it; `supavise projects pause|resume <ref>` forces it).
- **The writable artifact directory is a persistence path.** `artifacts/postgres/` is writable in every project's Postgres namespace and shared by all clusters, the system cluster that holds the registry included. One cluster can replace the Postgres binaries that every other cluster, and the control plane's own database, run at their next restart. It is writable only because of the launcher's one `chmod +x` of `share/supabase-cli/config/pgsodium_getkey.sh` under `set -e`, which fails on a read-only or foreign-owned tree. The fix is not done: keep the artifact tree root-owned and read-only, give each cluster a private writable copy of only `share/supabase-cli/config` (a per-project `BindPaths=` rendered by the plane), drop `artifacts.handOver`, and make the upstream chmod conditional.

### Checking the metadata rule

CI machines have no instance metadata service, so `imds_up` (`tests/linux/lib.sh`) puts a mock on both addresses (`ip addr add 169.254.169.254/32 dev lo`, `ip -6 addr add fd00:ec2::254/128 dev lo`). `imds_blocked_in <unit>` moves a `curl` into the unit's cgroup, where systemd's BPF filter applies, and expects it to fail while the same `curl` outside reaches the mock; `systemd-smoke.sh` also runs `COPY (select 1) TO PROGRAM 'curl ...'` inside a project's Postgres, the real attack path. By hand on a node, `sudo bash -c 'echo $$ > /sys/fs/cgroup$(systemctl show -p ControlGroup --value supavise-gotrue@<ref>.service)/cgroup.procs && exec curl -m 3 http://169.254.169.254/'` fails with "Operation not permitted" while the same `curl` from a plain shell reaches the metadata service.

## Future hardening: one uid per project

The real fix changes a project-wide convention, so it is recorded and not done: a distinct uid per project (and one for the fleet and one for the control plane), with the environment files owned by the project uid and still read by systemd as root, so that the kernel denies `/proc` access across projects. Costs: uid allocation and cleanup in `lifecycle`, file ownership in `internal/units` and the backup paths, and the installer (`DynamicUser=` does not fit, because the data directories must keep a stable owner). On systemd 257 or later, `PrivatePIDs=yes` per unit would hide other units' processes without new uids. Until one of them ships, this page is the supported trust model.

## Residual notes

- The singleton `system/<svc>` directories are optional (`-` prefix): create one before a service needs to write there.
- `pg_hba.conf` trusts `supabase_admin` on the cluster's private unix socket (a directory only the `supavise` user can enter) and requires scram-sha-256 on TCP. The registry is reached through that socket, so a process that can enter a cluster's socket directory is a superuser there. The allowlist hides every socket directory from the other units, but not from the daemon, which needs them.
- **Cloud metadata.** On AWS (`deploy/cloudformation/supavise.yaml`) the instance role holds write access to the whole backup bucket and TXT changes for `_acme-challenge` names in one Route 53 zone, and IMDSv2's hop limit of 1 does not stop a process on the instance itself, so every `supavise-*` unit denies the metadata addresses. WAL archiving does not use the role inside Postgres (the daemon does), so only `supavise.service` and the `supavise-basebackup` units use it. `supavise-storage` cannot use it either: its S3 backend (`[fleet] storage_backend = "s3"`) needs a static key (`storage_s3_access_key_id` and `storage_s3_secret_access_key`) scoped to the objects bucket, and `fleet.Setup` refuses to render the unit without one. The key sits in `config.toml` (0600, owned by `supavise`, hidden from every unit) and in the unit's own 0600 environment file.
- `supavise-edge-bundle@<ref>.service` also denies loopback, so a bundler cannot reach the Management API or a database. The `supavise` user cannot start it with `systemd-run`: the polkit rule grants `manage-units` only for names that start with `supavise-`, and polkit receives no unit name for a transient unit, so the sandbox is a fixed unit file.
